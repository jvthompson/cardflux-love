Overview

CardTable is a Windows desktop card-table application built on LÖVE2D (a Lua game framework on top of SDL2). It began life as a Flutter app — comments throughout the Lua source point back at the original .dart files each module was "ported" from — and that history still shapes the code: screens behave like Flutter widgets with a navigation stack, colors follow a Material 3 scheme (see theme.lua), and dialogs/menus mimic Flutter's modal navigator.

Four files form the skeleton everything else hangs off of:

conf.lua
LÖVE configuration callback — window setup, DPI awareness, test-mode module stripping.
main.lua
LÖVE entry point — defines love.load and all other love.* callbacks, and replaces love.run with a JIT-safe variant.
src/app.lua
The application shell (singleton App table): screen stack, custom title bar, global per-frame ticking, input routing, UI scale.
src/version.lua
Static version/build metadata consumed by the updater.

The LÖVE2D callback model

LÖVE does not have its own "main loop" that you write — instead, you define global callback functions (love.load, love.update, love.draw, love.keypressed, …) and the engine's default love.run calls them every frame: pump OS events, step the timer, call love.update(dt), clear the screen, call love.draw(), present. CardTable defines all of the standard callbacks in main.lua, each one just forwarding to the App singleton in src/app.lua (lazily required via a local A() helper so src/app.lua isn't loaded during test mode). This indirection keeps main.lua tiny and keeps all the actual behavior in one inspectable module.

conf.lua: window & test-mode setup

love.conf(t) runs before any window exists and configures LÖVE itself. CardTable's conf.lua does a few notable things:

  • Reads --test off arg directly (LÖVE hasn't parsed game arguments yet at this point) and stores the result in the global TEST_MODE, which both conf.lua and main.lua branch on.
  • Per-monitor DPI awareness on Windows (enableDpiAwareness): before the window is created, it uses LuaJIT's FFI to call SetProcessDpiAwarenessContext (falling back to the older SetProcessDPIAware on failure) so Windows gives the app real pixels instead of upscaling a 96-DPI bitmap. This is why the app can render crisp text at any monitor scale — the DPI scale is read back later in src/platform/window.lua and multiplied into App.effectiveScale() (see UI scale below). The whole call is wrapped in nested pcalls and skipped entirely off-Windows or in test mode.
  • Window defaults: title "CardTable", 1280×720 starting size, 960×600 minimum, resizable, borderless = true (the app draws its own title bar — see below), vsync on, 4x MSAA, highdpi = false (intentional — the app manages its own scale rather than letting LÖVE's high-DPI backbuffer handle it).
  • Test mode overrides: when TEST_MODE is set, the identity (save-folder name) becomes "cardtable_tests" so tests never read or write real user data, t.window = false skips creating a window at all, and the audio/sound/joystick modules are disabled.
  • Physics, video and joystick modules are disabled unconditionally — the app doesn't need them, so leaving them out trims startup time and binary surface.

main.lua: entry point & the custom love.run

love.load(args) is the first real callback LÖVE invokes. In test mode it hands off to runTests(args) (see below) and returns. Otherwise it supports a developer convenience, --identity <name>, which calls love.filesystem.setIdentity(name) to point the save directory at a separate folder — handy for running two instances as two different "players" locally. It then delegates everything else to require("src.app").load(args).

Outside test mode, main.lua defines the rest of LÖVE's standard callbacks (love.update, love.draw, love.keypressed, love.keyreleased, love.textinput, the mouse callbacks, love.wheelmoved, love.resize, love.filedropped, love.directorydropped, love.focus, love.quit), each one a one-line forward to the matching App.* method.

Why love.run is overridden

The most unusual piece of main.lua is that it replaces love.run itself, rather than relying on LÖVE 11's default implementation. The code comment explains why: the custom title bar's window drag/resize behavior (src/platform/window.lua) installs an SDL hit-test callback — a native C callback that SDL invokes from inside love.event.pump to ask "what's under this point, titlebar or client area?". That hit-test callback is itself implemented as an FFI callback from Lua. LuaJIT's JIT compiler cannot re-enter an FFI callback from a C call made by already-compiled (JIT'd) code — doing so would crash or misbehave. The fix is jit.off(loop): the per-frame loop closure returned by love.run is explicitly excluded from JIT compilation, forcing it to run in the interpreter so the FFI callback path stays safe. Apart from that one addition, the loop is a faithful reproduction of LÖVE 11's default love.run: pump events, dispatch love.handlers[name] for each queued event (intercepting "quit" to consult love.quit() first), step the timer, call update, then if graphics is active clear/draw/present, then sleep 1ms to avoid pegging a CPU core.

This is a good example of the kind of constraint that only shows up once you combine two features (a native hit-test callback and a JIT compiler) — worth remembering if the window-dragging code ever needs to change.

Test mode

When invoked with --test, main.lua's runTests scans the tests/ directory (via love.filesystem.getDirectoryItems) for every file matching *_test.lua, sorts them for determinism, and hands the list to require("tests.runner").run(files, filterArg). An optional second CLI argument after --test (as long as it doesn't itself look like a flag) is used as a name filter so a single test file/case can be targeted. The process exits with code 0 or 1 via love.event.quit(ok and 0 or 1) — this is what lets the test suite run headlessly from a shell/CI without a window (recall conf.lua sets t.window = false in this mode). Full detail on the test runner and individual suites lives on the Tests & Tools page.

version.lua

A plain data module returned as a table: name (semantic version, e.g. "0.2.0"), build (an integer that increases with every release and is compared against GitHub release tag suffixes like "+10"), releaseRepo ("jvthompson/cardtable"), releaseAssetName ("cardtable-windows.zip"), and exeName ("CardTable.exe"). The in-file comment explains why the build number is independent of any other numbering scheme in the project: the LÖVE port is versioned separately from the original Flutter app it was ported from, and must publish releases to its own GitHub repository — if it reused the Flutter repo's build numbers, the updater would never see a build number higher than what's already there and would think it's always up to date. This table is consumed entirely by src/platform/updater.lua, which polls releaseRepo's GitHub releases, compares build against the latest tag, and if newer, downloads releaseAssetName and replaces exeName.

src/app.lua: the application shell

src/app.lua returns a single table, App, that acts as a global singleton for the whole running process — every screen, dialog and background system reaches back into it. Its responsibilities: own the navigation stack of "screens", draw the custom borderless-window title bar, route every LÖVE input callback to the UI framework and the active screen, tick the handful of systems that must keep running regardless of which screen is on top (network sockets, image decoding, Discord presence, the updater), and track cross-screen state like the player's profile and UI scale setting.

The screen stack

App keeps a local array stack of screen objects (not exposed directly; manipulated only through the functions below). This is a classic push-down navigator, equivalent to a Flutter Navigator:

App.push(screen)

Pushes screen on top, blurs the UI focus (ui.blur() — closing e.g. an open text field so it doesn't bleed into the new screen), and calls screen:enter() if present.

App.pop()

Pops the top screen, calling its :leave() if present, blurs focus, then calls :resume() on the screen now on top (if any) so it can refresh itself (reload data that may have changed while it was covered).

App.replace(screen)

Pops the current top (calling :leave()) and pushes screen in its place — used when a screen should not remain in the back-stack (e.g. moving from a lobby into an active game).

App.popToHome(message)

Unwinds the entire stack down to the bottom screen (assumed to be Home), calling :leave() on everything removed, closes any open menus (overlays.closeMenus()), and sets home.message so Home can show an orange banner (e.g. "You were disconnected") before calling :resume() on it. Used for abnormal exits from deep in a flow — disconnects, kicked-from-game, fatal errors — without having to pop one frame at a time.

App.top()

Returns the current top-of-stack screen (or nil if empty).

The screen contract

A "screen" is a plain Lua table/object with no required base class — it just needs to optionally implement whichever of the following fields or methods are relevant to it (all are duck-typed, checked with if screen.x then):

MemberPurpose
titleString shown in the custom title bar while this screen is on top.
showBackWhether the back arrow is shown in the title bar (default true whenever the stack has more than one entry).
onBack()Overrides what the title bar's back button does; if absent, it just calls App.pop().
draw(x, y, w, h)Called every frame inside the UI frame, given the content area below the title bar (and below the top-level clip App.draw pushes).
update(dt)Per-frame update, called only while the screen is on top of the stack.
backgroundUpdate(dt)Per-frame update called for every screen on the stack, even ones buried underneath others — used by screens that must keep ticking state (e.g. a network connection) while a dialog/sub-screen is pushed above them.
keypressed(key, scancode, isrepeat) / keyreleased(key, scancode)Forwarded only when the UI framework and any open overlay didn't already consume the key.
textinput(text)Forwarded only when no focused text field consumed it first.
enter()Called once, right after being pushed.
leave()Called once, right before being popped/replaced.
resume()Called when this screen becomes the top again after something above it was popped (or after popToHome).
filedropped(file) / directorydropped(path)OS drag-and-drop forwarded to the top screen only.
quit()Return true to veto the app closing (e.g. to show an "are you sure" dialog first) — see App.quit.
forceLightThemeWhen truthy, App.draw forces theme.c = theme.light for this frame regardless of the user's dark-mode setting — used by the game table, which (like Flutter's own Theme(data: AppTheme.light) override around the table) is always rendered in light colors so felt/cards read correctly.

Screens live under src/ui/screens/ (general), src/ui/screens/gamedef/ (the game-definition editor), src/ui/screens/server/ (multiplayer lobby) and src/ui/table/ (the game table itself).

Player profile

App.profile is a plain table ({ name, color, avatarPath }) shared by every screen that needs to show "you" — defaulting to name = "Player" and a blue-gray ARGB color. App.loadProfile() pulls the persisted values from src/data/profile.lua (getName, getColor, getAvatarPath) and is called once from App.load. App.playerName() trims whitespace from the profile name and falls back to "Player" if it's empty — the single accessor every screen should use rather than reading App.profile.name directly, so blank names never leak into UI or network messages.

Discord join invites

App.showDiscordJoinPrompt(secret) is the callback wired up to discord.onJoinSecret from App.load. Discord Rich Presence invites encode the host as a "host:port" secret string; discord.parseJoinSecret(secret) splits it, and if valid, App raises a confirm dialog ("Join the CardTable game at host:port?") whose confirm action pushes a Join screen pre-filled with { host, port, autoConnect = true } — this is also how a friend's "Join Game" click in Discord can cold-launch the app straight into a connection attempt, since discord.init() is set up this early in App.load.

UI scale & DPI

The UI is authored in fixed "logical units" (e.g. a button is always 40 units tall) and LÖVE draws everything scaled up by a single factor via love.graphics.scale(theme.scale) in App.draw, so the same layout code produces sharp output at any display density. That factor is computed by:

App.effectiveScale()

window.dpiScale() * App.uiScaleSetting(), i.e. the monitor's own DPI scale (from src/platform/window.lua, populated using the DPI awareness enabled in conf.lua) multiplied by the user's manual UI-scale preference. The result is then clamped so a maximized window never shrinks below the logical minimum size: it takes window.desktopSize() and caps the scale at min(scale, desktopW/960, desktopH/640) (640 = 600 + 40 for the title bar), and finally clamps to at least 0.5.

App.uiScaleSetting() / App.setUiScaleSetting(v)

Reads/writes the user's chosen multiplier from src/data/settings.lua under settings.keys.uiScale, clamped to [0.5, 3]; setting it back to exactly 1 removes the stored key instead of writing 1 explicitly (keeps the settings file clean). The selectable presets are App.uiScaleOptions = {0.75, 0.9, 1, 1.1, 1.25, 1.5, 1.75, 2}, consumed by the scale picker in Settings.

applyScale(force) is a local function that recomputes the scale every frame (cheaply short-circuiting if unchanged, unless force), and when it does change calls theme.setScale(s) (rebuilds font caches at the new pixel density — see theme.lua) and window.setScale(s), then recomputes and applies the window's minimum size in physical pixels via window.setMinimumSize. It's called once with force = true during App.load (right before maximizing the window) and unconditionally every frame from App.update, and also on F11 (toggling the window frame changes the available size).

Mouse coordinates from LÖVE arrive in physical pixels; App.mousepressed/released/moved divide by theme.scale before forwarding to the UI framework (ui.onMousePressed etc.), so all UI and screen code only ever sees logical coordinates.

The custom title bar

Because conf.lua sets t.window.borderless = true, the OS supplies no title bar, minimize/maximize/close buttons, or drag handle — App draws its own (drawTitleBar(w), called from App.draw whenever not window.framed — i.e. the user hasn't toggled back to a native frame with F11). It fills a TITLE_H-tall strip (window.titleBarHeight) with theme.fixed.titleBar, draws a back arrow (if the stack is deeper than one and the top screen allows it), the screen's title, and three icon buttons on the right: dark/light mode toggle (flips theme.setDark and persists via profile.setDarkMode), maximize/restore (window.toggleMaximize, checking love.window.isMaximized()), and close (love.event.quit()).

The draggable region of the title bar — the strip between the end of the title text and the start of the button row — is reported to src/platform/window.lua through window.setDragArea(fn), a predicate called by the native window hit-test (the same FFI hit-test discussed in why love.run is overridden) to decide whether a click there should drag the window like a native title bar would. titleButtons.titleEnd / titleButtons.buttonsStart are recomputed every frame drawTitleBar runs, so the hit-test always reflects the current title text's width.

Developer hooks

App.load scans args for several developer-only flags (none of which affect normal play), stored in a local dev table and processed every frame by devTick() (called first thing in App.update):

FlagEffect
--no-discordSkips discord.init() entirely.
--update-checkForces the updater to check even if it normally wouldn't yet (passed to updater.check(forceUpdateCheck)).
--eval "<lua>"On frame 3, compiles and runs the given Lua string once, with App injected into scope (via a metatable __index fallback to _G) — a quick way to poke at live state without rebuilding.
--shot <file.png>On frame (dev.frames or 30), calls love.graphics.captureScreenshot(file); two frames later the app quits. Useful for automated visual checks of a screen reached via --script.
--frames NOverrides which frame the screenshot above is taken on (default 30, giving the UI time to settle).
--script <file.lua>On frame 3, loads the file (its chunk must return a function taking one argument, api) and runs it as a coroutine resumed once per frame, after installing fake-key support (see below).
--dark / --lightForces dark/light theme at startup, bypassing the persisted preference — handy for deterministic screenshots.

The --script API (built by makeScriptApi()) gives a scripted test/demo coroutine a small vocabulary for driving the UI exactly like a real user, entirely in logical coordinates (it multiplies by theme.scale internally before calling App.mouse*):

FunctionBehavior
api.wait(n)Yields the coroutine for n frames (default 1).
api.move(x, y)Moves the fake cursor, forwarding to App.mousemoved.
api.press(x, y, b) / api.release(x, y, b)Moves (press only) then fires App.mousepressed/App.mousereleased for button b (default 1).
api.click(x, y, b)press + release in sequence.
api.doubleClick(x, y)Two press/release pairs with the second carrying presses = 2, matching real double-click semantics.
api.drag(x1, y1, x2, y2, steps)Press at the start, interpolate move calls across steps (default 10), release at the end.
api.key(k)A tap: keypressed then keyreleased.
api.keyDown(k) / api.keyUp(k)Sets/clears an entry in a local fakeDown table that love.keyboard.isDown is monkey-patched (installFakeKeys) to consult first — lets a script simulate held modifier keys (e.g. holding Shift across several other calls), which fake press/release alone can't represent.
api.text(t)Fires App.textinput(t) — for typing into fields.
api.shot(name)Immediate screenshot, not tied to the --shot/--frames timer.
api.quit()Calls love.event.quit() then yields (the coroutine won't be resumed again).
api.log(...)print(...) — visible in the console when one is attached.
api.appThe live App table itself, for scripts that need to reach further (e.g. directly inspecting a screen's state).

If the script coroutine errors, devTick prints the error and force-quits with exit code 1 — so a broken scripted smoke test fails loudly rather than hanging.

LÖVE callback forwarders & the global tick

App.update(dt) is the heart of the per-frame tick and runs regardless of which screen is active:

  1. devTick() — process scripted/eval/screenshot developer hooks.
  2. window.update() — platform window bookkeeping.
  3. applyScale() — recompute/re-apply DPI+user scale if it changed.
  4. imageCache.update() — drain decoded images from the background worker (data/image_cache.lua).
  5. protocol.updateAll(dt) — ticks every live network connection object (net/protocol.lua), so a socket kept open by a screen two levels down the stack still gets serviced.
  6. netinfo.update() and upnp.update() — background network/UPnP discovery state machines.
  7. discord.update(dt) — services the Discord Game SDK's callback loop.
  8. updater.update() — advances any in-progress self-update download.
  9. Every screen still on the stack gets :backgroundUpdate(dt) if it defines one (so buried screens can keep state fresh).
  10. Finally, only the top screen gets its own :update(dt).

The reasoning for running steps 2–8 unconditionally (rather than only while their "owning" screen is on top) is in the source comment: these are process-wide systems — a host server or a client connection, once opened, must keep accepting/sending data even while the user has a settings dialog or a deck editor pushed on top of the table screen, or the connection would stall and time out.

App.draw() computes the logical window size from the physical framebuffer size divided by theme.scale, applies love.graphics.scale, optionally forces the light theme for screens with forceLightTheme, starts a UI frame (ui.beginFrame), fills the background, clips to the content area below the title bar and calls the top screen's :draw(x, y, w, h), draws the title bar (if not using a native frame), draws all queued overlays (overlays.draw()), ends the UI frame (ui.endFrame()), and finally re-derives theme.c from theme.isDark rather than restoring a saved value — because the title bar's dark-mode button may itself have just flipped theme.isDark this same frame.

App.keypressed special-cases F11 (toggle title-bar frame, then applyScale(true) since changing frame mode resets the OS minimum-size constraint) and Escape while any overlay is open (routed to overlays.keypressed even if a text field elsewhere has focus, so Escape always closes dialogs first). Otherwise keys go to ui.onKeyPressed first (consumed if a text field has focus), then to overlays.keypressed if any overlay is open, and only then to the top screen's own :keypressed. textinput follows the same "UI focus first" precedence. The mouse/wheel forwarders simply divide physical coordinates by theme.scale and pass straight through to the UI framework's hooks (see UI Toolkit: input model).

Shutdown (App.quit)

App.quit() is wired to LÖVE's love.quit callback, which — per the custom love.run — can veto the quit entirely by returning true. App.quit walks the screen stack top to bottom and calls each screen's own :quit() if present, stopping (and returning true itself) at the first one that returns true — e.g. a screen mid-game might pop up "Are you sure you want to quit?" and veto the close until confirmed. If nothing vetoes, it tears down process-wide systems before allowing the real exit: protocol.stopAll() (closes every open network connection/socket cleanly), imageCache.shutdown() (stops the background image-decode worker thread), and discord.dispose() (releases the Discord SDK).
