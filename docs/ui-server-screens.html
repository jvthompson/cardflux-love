Overview & screen flow

This directory (src/ui/screens/server/) holds every screen that only exists while the client is connected to a CardTable Server — the companion Go lobby server documented on CardTable Server (Go). A player reaches this stack from multiplayer.lua's "Join Game" flow, which opens a TCP connection and hands it to these screens as a src/net/server_client.lua instance (sc in nearly every file here — see Networking for the wire protocol and connection lifecycle).

The screen stack flows roughly like this:

login.lua  --(sign in / register)-->  lobby.lua
lobby.lua  --(Create Game / Join / Watch)-->  room.lua  --(host starts)-->  table (ui-table.html)
lobby.lua  --(header buttons)-->  decks.lua | collection.lua | shop.lua | admin.lua
lobby.lua  --(Ask to Trade)-->  trade.lua

Every one of these screens is a plain Lua table built with setmetatable following the App screen-object contract described in Architecture & App Lifecycle (title, draw(x,y,w,h), optional onBack(), update(dt), etc.), and they are all built from the immediate-mode widgets in the UI toolkit (ui, theme, overlays, widgets).

common.lua — shared helpers

src/ui/screens/server/common.lua
Helpers shared by every server screen: downloading a game before use, entering/leaving rooms, a user avatar+name row, and time formatting.

Rather than a base class, CardTable shares behavior between these screens through a small module of free functions. Every other file in this directory requires it as common.

M.withGame(sc, gameId, onReady)

Makes sure the local copy of a server game is present and current before using it. It calls assetSync.ensureGame (see asset_sync.lua) which diffs the server's game folder against the client's cache and downloads anything missing or changed. While that's in flight it shows a non-dismissible progress dialog ("Downloading <game>...") built with overlays.dialog, reporting files-done/total and bytes downloaded, and a note that already-cached files are reused. Once ready, onReady(game) runs with the fully loaded GameDefinition (see src/core/models.lua).

M.returnToLobby(message)

Pops every screen above the server lobby (identified by screen.isServerLobby == true, a flag only lobby.lua sets), then shows message as a toast if given. Used whenever a room/game/trade ends and the player needs to land back at the lobby regardless of how many screens are currently stacked above it.

M.gameScreen(sc, game, spectating)

Builds the actual gameplay screen for a running room: a MP.ClientGame instance from src/ui/screens/multiplayer.lua, which wires the room's live game channel to the shared table screen. Spectators are given the id "spectator:" .. sc.self.id (matching a filtering convention the server applies for watch-only viewers). Passes through collectionMode (from the room), a deckStore bound to this server (deckStore.serverStore(sc), see data.html), and an onExit callback that sends roomLeave, closes the game channel, and either pops all the way home (if the connection itself dropped) or returns to the lobby.

M.enterRoom(sc, room, mode)  ·  M.openRoomScreen(sc, game, room)

enterRoom is the single entry point lobby.lua uses for both "Join" and "Watch" (mode is "join" or "spectate"). It first ensures the game is downloaded (withGame), then re-opens the client's game channel before sending the roomJoin/roomSpectate request — the comment in the code explains why: a room that's already playing pushes gameData + fullState immediately after the reply, so the channel must already exist to catch them. On success it records sc.roomId / sc.spectating and calls openRoomScreen, which pushes either the table (if room.state == "playing") or room.lua (if still waiting for players).

M.userRow(sc, user, x, y, w, opts)

Draws the small avatar + name row reused by the lobby's user list, the room's seat list, and admin dialogs. Resolves the user's cached avatar image via sc:avatarKey(user.avatarHash) and defers to widgets.avatar for the actual drawing.

M.timeLabel(at)

Formats a Unix timestamp as HH:MM for chat timestamps.

login.lua — sign in / create account

src/ui/screens/server/login.lua
First screen after connecting: resumes a remembered session, or collects email/password (or a new account's details).

L.new(sc) looks up a saved session for this server via SC.savedSession(sc.key) (SC = src/net/server_client.lua, keyed per-server so multiple servers each keep their own remembered login). If a session exists and was saved with "Remember me" checked, it immediately fires a resume request with the stored token so the player skips straight to the lobby; a session saved before "Remember me" existed is discarded rather than silently auto-signing-in. If resume fails, the stored session is forgotten and the normal sign-in form shows (with the saved email pre-filled unless it's a "disconnected" error).

The screen has two modes, toggled by a ui.segmented control when the server allows registration (sc.info.registrationOpen):

  • Sign In (L:submitSignIn) — email + password, "Remember me" checkbox. Sends login with passwordHash = SC.passwordHash(email, password) — the password is hashed client-side before it ever goes on the wire (see the Security notes on CardTable Server (Go)).
  • Create Account (L:submitCreate) — validates email format, password length (≥6) and confirmation match, lets the player pick a name, color (colorpicker.field) and an optional avatar image (via file_dialog.lua, resized by profile.resizeAvatarBytes and base64-encoded for the register request).

Both paths funnel into L:signedIn(r, email, remember), which stores sc.token and sc.self, persists or clears the remembered session (SC.saveSession / SC.clearSession), and replaces this screen with lobby.lua. L:onBack() disconnects the socket entirely rather than just popping the screen.

lobby.lua — the server lobby

src/ui/screens/server/lobby.lua
The server's hub: a list of games (rooms) to join/watch, server-wide chat, who's online, and the entry points into Deck Editor, Card Shop, Collection and Admin.

This is the largest and most central of the server screens. Lobby.new(sc) sets isServerLobby = true (the flag common.returnToLobby looks for) and subscribes to several server-pushed events via sc:on(event, handler):

EventHandler behavior
disconnectedPops all the way to Home with the disconnect reason.
roomClosedIf this client was in that room (mine), closes the game channel and returns to the lobby with a human-readable reason from CLOSE_REASONS (closed by owner, idle timeout, start error).
tradeInviteLobby:onTradeInvite — another player wants to trade; shows an accept/decline dialog that sends tradeRespond.
tradeClosedLobby:onTradeClosed — the trade we sent/received closed (declined, expired, left, completed); closes whichever waiting dialog is open and, if the Trade screen is currently showing, returns to the lobby with a message.
tradeLobby:onTradeUpdate — a trade we're part of just started or changed; pushes trade.lua if it isn't already showing.

Note the comment in onTradeClosed explaining a deliberate design choice: whether the Trade screen is currently open is read directly off app().top() rather than tracked in a separate boolean, because a flag set only when this code pushes Trade and cleared only when this code pops it would get stuck in states reached some other way (e.g. the server pushing tradeClosed only to the other player).

Creating a game

Lobby:openCreateGame() pushes a small inline screen (GameChoice, defined in this file) that reuses decks.drawGameList to show the server's games as tiles. Picking one pops back to the lobby and opens Lobby:openCreateGameDialog(game) — a dialog for a name and player count (1–8) — whose "Create" action calls Lobby:createGame(st): downloads the game (common.withGame), opens the game channel, then sends roomCreate and on success stores sc.roomId and calls common.openRoomScreen.

Trading

Lobby:askToTrade(u) reuses the same GameChoice tile picker to choose which game to trade cards from, then Lobby:sendTradeRequest(u, g) sends tradeRequest and shows a "Waiting for <name> to respond..." dialog with a spinner until the trade or tradeClosed event resolves it. The entry point for this is a right-click context menu on another online user's row in drawUsers — only offered when collection mode is on and that user isn't currently in a room.

Profile editing

Lobby:openProfile() is a large dialog for editing the player's name, avatar, color and (optionally) password on this specific server — distinct from the local App.profile edited in settings_dialog.lua, since a server account can have its own name/avatar/color per server. "Save" builds a minimal diff payload (only changed fields) for profileUpdate; "Log Out" calls Lobby:logOut(), which clears the remembered session and sends logout.

Drawing: three-pane layout

Lobby:draw(x, y, w, h) lays out a header (drawHeader — server name/MOTD on the left, profile button, Admin/Collection/Deck Editor/Card Shop buttons and the token balance chip on the right, each only shown when relevant — e.g. Admin only for sc:isAdmin(), Collection/Shop only in collection mode) above three columns: a scrollable room list (drawRooms → drawRoom per room, with Join/Watch/Rejoin/End buttons depending on state and ownership), a chat pane (drawChat, auto-scrolls to the newest message), and — only when the window is wide enough (w >= 1180) — an online-users column (drawUsers, right-click menu for trade invites, admin shield icon).

room.lua — pre-game seating

src/ui/screens/server/room.lua
A created-but-not-started game: seat list (reorderable by the creator) and room chat. Hands off to the table once the host starts it.

R:update() is the key mechanism here: it polls sc.channel.lastGameData every frame, and the instant it becomes set (the server just started the game and pushed gameData) it replaces this screen with common.gameScreen(...) — the comment notes fullState arrives right after gameData, so the table screen picks it up once mounted.

The room owner (room.ownerId == sc.self.id, and not spectating) sees up/down arrows next to each occupied seat (R:moveSeat, sends roomSeats with the new order — seat order becomes turn order) and a "Start Game" button (R:start, sends roomStart). Everyone else sees a spinner and "Waiting for <creator> to start the game...". R:onBack() sends roomLeave and closes the channel. drawChat mirrors the lobby's chat widget but scoped to sc.roomChat and tagged with roomId on send.

decks.lua — server deck editor entry

src/ui/screens/server/decks.lua
Pick one of the server's games, then open the shared Deck Editor against server-stored decks (and, in collection mode, a card pool limited to owned copies).

This file's most reused export is D.drawGameList(sc, id, x, y, w, h, subtitle, onPick, opts) — a generic "choose one of this server's games" tile grid built on game_picker.lua's GamePicker.drawGrid. It's called not just from this screen's own draw, but also from lobby.lua's GameChoice, collection.lua, shop.lua, and anywhere else a "pick a game on this server" step is needed — opts.excludeStandardDeck hides the built-in 52-card deck where it wouldn't make sense (e.g. decks, collection, shop).

D:open(info) downloads the game, builds a deckStore.serverStore(sc), and — in collection mode — first fetches collectionGet so the editor can be told which cards (and how many copies) the player actually owns (ownedQty), restricting what can be added to a deck. It then pushes src/ui/screens/deck_editor.lua's Editor (documented on Screens) configured with that store.

collection.lua — browse owned cards

src/ui/screens/server/collection.lua
Collection mode only: browse every card you own for a game, with filters, an "Owned only" toggle, and ownership-count badges. Packs are bought elsewhere (shop.lua).

C:open(info) downloads the game and fetches collectionGet to get r.cards — a map of definitionId → ownedCount. C:drawCollection renders the same card-pool tile grid used by the Deck Editor's pool (POOL_SCALE = 4/3 larger than table size, 3 lines of name, reusing card_render.lua's CR.draw), filtered by the shared card_filter_bar widget plus a local "Owned only" checkbox.

Cards marked isFreeCard are always shown as owned (∞ badge) and excluded from the distinct/total counts; everything else shows a ×N badge for owned copies and is drawn at 25% alpha when the count is zero (so the full card list is still browsable, just visibly "not yours yet"). Hovering while holding Space shows the same large card preview used throughout the app (CR.drawPreview). unownable cards (the collection-mode equivalent of "always available") are filtered out entirely since they're never part of a collection.

shop.lua — card shop (packs & starters)

src/ui/screens/server/shop.lua
Collection mode only: spend tokens on booster packs per set, and on starter decks. Reuses the Pack Generator's own algorithm, executed on the server.

S:drawShop shows the player's token balance and per-pack/per-starter cost (server-configured, see admin.lua's Server settings tab), then a tile grid of the game's sets (as packs) using set art resolved via image_resolver.lua's resolveImageAnyExt, falling back to the game's default card back image. A second row of tiles covers starter decks, read from self.info.starterDecks (metadata sent alongside the game list).

S:buyPack(set)

Sends packBuy with the game and set id. The server runs the same pack-opening algorithm as the Pack Generator widget (src/core/pack_generator.lua) — see the note on server.html about the server executing a mirrored copy of the client's Lua rules via gopher-lua. On success it updates the local owned-card tally and sc.self.tokens, then reveals the pack.

S:buyStarter(starter)

Sends starterBuy; on success the granted cards are both added to the collection and saved as a new deck on the server (toast shows r.savedName), then the pack reveal plays with the starter's name as the title.

S:revealPack(cards, title)  ·  S:showPackSummary(cards, title)

The opened pack is revealed one card at a time in a dialog ("Next Card" / "Show All" once on the last card, or "Skip" to jump straight to the summary) — each new-to-the-collection card gets a green "NEW" badge (newBadge). showPackSummary then lays out every card from the pack in the same tile-grid style as the pool, with the Space-preview overlay available while hovering.

trade.lua — player-to-player trading

src/ui/screens/server/trade.lua
Collection mode only: two players build "want" offers by dragging cards from each other's collections; the server swaps everything once both sides confirm.

T.new(sc, game) sets isTradeScreen = true (the flag lobby.lua's onTradeClosed/onTradeUpdate check for) and immediately requests both parties' collections (T:refreshMine via collectionGet, T:refreshTheirs via tradeCollectionGet — a trade-scoped variant so a player can see what their counterpart owns without a general "view anyone's collection" permission).

Drag-to-offer

This is the one screen in the server UI that implements its own custom drag gesture rather than reusing the table's drag system. T:updateDrag() runs a simplified press→threshold→drag state machine (DRAG_THRESHOLD = 4 px, same idea as table_screen.lua's drag pipeline but trimmed to a single fixed drop target): pressing a card in the partner's collection grid (T:drawGrid with draggable = true) arms self.pressing; moving past the threshold promotes it to self.dragging; releasing over self.myWantBoxRect sends tradeOffer with delta = 1. T:drawDragFeedback draws the floating card and highlights the want-box while hovering it.

Removing a card from your own want box is just a click (not a drag) — each tile in T:drawWantBox is a clickable region when mine == true, sending tradeOffer with delta = -1.

Layout

Two "Wants" boxes side-by-side at the top (yours and theirs — T:drawWantBox, populated from trade.offers[partyId].cards), a tab bar below switching between "Your Collection" and "<name>'s Collection" grids (only the partner's is draggable), a Confirm/Confirmed button (T:drawConfirm, sends tradeConfirm), and a chat pane on the right scoped to sc.tradeChat. T:onBack() confirms, then sends tradeLeave.

admin.lua — server administration

src/ui/screens/server/admin.lua
Admin-only screen (sc:isAdmin() gate in lobby.lua): four tabs — Users, Server, Games, and Files. 655 lines, the largest server screen.

A.new(sc) immediately refreshes two independent datasets: A:refreshUsers() (adminUsers) and A:refreshSettings() (adminSettingsGet, which also returns gameErrors — problems found while loading game folders — and populates self.form, a text-editable mirror of the settings used so number fields can be typed freely before being parsed back on save). The four tabs are a widgets.tabBar.

Users tab — A:drawUsers

A searchable (self.search filters by name or email), scrollable table of every account: name, email, token balance, and status tags (Admin / Disabled / Online). Clicking a row opens A:editUser(u), a dialog covering:

  • Name, email, "Server admin" and "Account disabled" switches (disabled toggle is itself disabled for your own account to prevent self-lockout).
  • Token balance (direct tokensSet) and a separate "Grant (adds)" field (tokensAdd, can be negative) — sent as a diff so only touched fields are included in the adminUserUpdate request.
  • Password reset (hashed with the new email if that's also changing, before sending).
  • "Clear collection" for a chosen game — a destructive, confirmed action (adminClearCollection) that leaves existing decks intact but missing those cards.
  • "Disconnect" (adminKick) and "Delete Account" (adminUserDelete, confirmed, destructive) — both hidden for your own account.

Server tab — A:drawServer

A single scrollable form, organized under sectionLabel headers:

  • General — server name, MOTD, "Allow new accounts" switch.
  • Cards — Free Play vs. Collection mode segmented control (with inline help text explaining the consequence of switching), starting tokens, pack cost, starter-deck cost, allowance amount and period (Never/Daily/Weekly).
  • Limits — idle game timeout, max concurrent rooms (0 = unlimited), chat history length.
  • Shutdown — A:drawShutdown: either a "Shut Down Server" button (confirmed, sends adminShutdown — a graceful shutdown that blocks new connections and waits up to 5 minutes or until everyone leaves) or, while one is pending, a live countdown read from sc.shutdownAt.

A:saveSettings() parses every text field back to a number (falling back to the previous value if unparseable) and sends adminSettingsSet.

Games tab — A:drawGames

This tab was added recently (see the git history entry "Add a server admin Files tab and Games tab game management"). It lists every game folder the server has scanned, with card/set counts and the folder id, plus:

  • Upload New Game (A:uploadGame) — opens a native/in-app zip file picker (file_dialog.lua) and streams it to the server via AGM.installFromZip (admin_game_manager.lua), showing upload progress as a percentage.
  • Rescan Games Folder — sends adminRescanGames, refreshing sc.games and any gameErrors (shown inline in red below the list).
  • A delete icon on any g.removable game (A:removeGame, confirmed, destructive — calls AGM.remove).
  • Below that, a live list of running rooms with an "End" button per room (confirmed, sends adminCloseRoom) — this duplicates the lobby's own per-room "End" for owners/admins but gives admins one place to end any room.

Files tab — A:drawFiles

Also new per the same commit. A per-game file browser over the server's actual game folder, built around admin_file_manager.lua (AFM):

  • A game dropdown switches which game's folder is browsed (resets to the folder root and re-lists on change).
  • Upload (A:uploadFile) — picks a local file and streams it to the current folder path via AFM.upload, with a progress percentage.
  • Breadcrumb navigation (A:drawFileCrumbs) — clickable "GameName / sub / folder" trail built by splitting self.filesPath on /; an "up one level" icon button strips the last segment.
  • A directory listing (AFM.list) showing folders and files with sizes (formatBytes); clicking a folder row navigates into it (A:navigateFiles).
  • A delete icon per entry (A:deleteFile, confirmed, destructive) with an extra warning specifically when deleting the game's own gamedef.json at the folder root, since that breaks the game until replaced.
  • A footnote that only image/JSON files are actually served to game clients — other uploaded file types just sit unused, which is a hint this tab is really meant for asset management (card art, set logos), not arbitrary file hosting.

Cross-cutting patterns

  • Diff-based update payloads. Both Lobby:openProfile's Save and A:editUser's Save build a json.object() containing only the fields that actually changed, rather than resending the whole record — a convention followed throughout this directory wherever a server mutation is partial.
  • Confirm-then-request for destructive actions. Every irreversible server call (end game, remove game, delete account, disconnect a user, clear a collection, delete a file, shut down the server) is gated behind overlays.confirm(..., { danger = true }) before the request is sent.
  • The request/callback convention. Every sc:request(name, payload, function(r) ... end) callback checks r.ok first and shows overlays.alert or a toast with r.message on failure — this is src/net/server_client.lua's request/response pattern, detailed on Networking.
  • Reused tile grids. The card-pool tile layout (POOL_SCALE = 4/3, 3 lines of name) appears near-identically in collection.lua, shop.lua's pack reveal, and trade.lua's grids, always built on card_render.lua.
