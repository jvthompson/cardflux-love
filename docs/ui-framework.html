Overview

Every visible pixel in CardTable — screens, dialogs, menus, the table itself — is drawn by the same small hand-written UI framework, src/ui/kit/. There is no retained widget tree: nothing is "created" once and updated later. Instead, every frame, screen code calls plain functions like ui.button("Save", x, y, w, h) which simultaneously draw the button and hit-test it against this frame's mouse state, returning whether it was clicked. This is the "immediate-mode GUI" (IMGUI) pattern — the same family as Dear ImGui or egui, just purpose-built in ~1100 lines of Lua for this app. Persistent state that a widget needs across frames (a text field's caret position, a scroll view's offset, whether a dropdown is open) is kept in small per-id tables inside ui.lua itself, keyed by a widget id the caller provides or that defaults to the widget's label and screen position.

ui.lua: the immediate-mode core

The module-level comment in the file states the model precisely: "Everything is drawn and hit-tested in absolute screen coordinates during love.draw. Input arrives through the ui.on* hooks (called from the LÖVE callbacks) and is consumed during the next frame." Concretely, src/app.lua's LÖVE callback forwarders (App.mousepressed, etc.) call ui.onMousePressed/onMouseReleased/onMouseMoved/onWheel/onKeyPressed/onTextInput to queue raw input into a module-local input table, and then App.draw brackets the whole screen draw with ui.beginFrame(w, h) / ui.endFrame(), during which every widget call reads that queue to decide hover/press/click state for itself.

Input model

The input table holds: mx, my (current mouse position, in logical units — already divided by theme.scale upstream); down[button] (held state); pressed[button] / released[button] (edge-triggered, true only on the frame the transition happened, cleared at the end of every endFrame); clicks[button] (the LÖVE "presses" count for that press — 2 signals a double-click); pressX/pressY (where a button went down, used by drag-threshold logic elsewhere in the app); wheelX/wheelY (accumulated this frame, consumable via ui.consumeWheel()); and two queues, keys and text, which only ever fill up while a text field has focus (ui.onKeyPressed/ui.onTextInput both check ui.focus before queuing, and return whether they consumed the event, which is how App.keypressed/textinput know whether to also forward to the active screen).

Low-level accessors built on this state: ui.mouse(), ui.mouseDown(b), ui.mousePressed(b), ui.mouseReleased(b), ui.clickCount(b), ui.wheel() (all default b to 1, left button). Most widget code doesn't call these directly though — it goes through ui.region (see Widget identity), which combines hit-testing with these primitives into one hover/press/click result.

Layers & covers (z-order hit-testing)

Because nothing is retained, the framework needs an explicit way to know which widget is "on top" when a dialog is drawn over a screen that's still being drawn underneath it (the screen keeps calling its own widget functions even while covered — it just shouldn't be able to receive clicks that a dialog above it is intercepting). The mechanism is layers and covers:

  • ui.overlay(fn) defers a draw function to run after the main screen body, each one bumping a layerCount and running in its own layer — this is how dialogs, context menus, dropdown popups and tooltips all stack above the screen and above each other (a dropdown's popup, itself drawn via an inner ui.overlay call triggered from within an outer overlay such as a dialog's content function, naturally lands one layer higher).
  • ui.cover(x, y, w, h) records that the current layer occupies a rectangle of the screen, and ui.coverAll() is the common case of covering the entire screen (also setting ui._modalOpenNext = true, which becomes ui.modalOpen() next frame — queried by code that needs to know "is some full-screen modal blocking the game table").
  • At the end of each frame, ui.endFrame() scans every cover recorded this frame and finds the highest layer whose rect contains the current mouse position — stored as topLayerAtMouse for next frame.
  • ui.hover(x, y, w, h) — the actual hit-test every widget ultimately calls — first checks layer == topLayerAtMouse; if the calling widget's current layer isn't the topmost layer under the mouse (as computed last frame), it reports "not hovered" regardless of geometry. This is exactly why a dialog visually on top of the screen also functionally blocks clicks to whatever's underneath it, with no manual "is a dialog open" checks scattered through screen code.
  • ui.baseHasMouse() exposes topLayerAtMouse == 0 directly, for code (like the game table) that does its own custom hit-testing outside the ui.region helper and just needs to know whether anything above the base layer currently owns the mouse.

Because covers accumulate within a frame as drawing proceeds, this scheme naturally supports arbitrarily nested popups (a menu's submenu, a dialog's own dropdown) as long as each nested piece is itself deferred through ui.overlay so it gets a higher layer number than its parent.

Widget identity

Interactive state that must persist across frames — which widget currently holds mouse capture, which text field has keyboard focus, a dropdown's open/closed flag — is keyed by a widget id, a string. Most widgets accept an explicit opts.id; if omitted, ui.defaultId(label, x, y) builds one from the label text, the widget's screen position (floored to integers) and the current layer — adequate as long as two widgets with the same label never sit at the exact same position in the same layer, which is true for static layouts but not safe for widgets inside a loop (e.g. a list row rendered per item) — those call sites pass an explicit id incorporating the loop index or item key instead (see e.g. Reorder:handle(i, ...) in widgets.lua, which builds self.id .. ":h" .. i).

ui.state(id) is the generic escape hatch: lazily creates and returns a persistent per-id table in widgetState, used by composite widgets (dropdowns, filter menus, the reorder helper) to stash whatever ad-hoc fields they need (open, dragging, cached picks, …) without the core framework needing to know about them.

ui.region(id, x, y, w, h, opts) is the single workhorse hit-test/interaction primitive almost every clickable widget is built from. It computes hovered via ui.hover; if hovered and a press just happened, claims mouse capture (ui.active = id), sets pressed = true, and flags doubleClicked when clicks[1] >= 2; flags rightClicked on a hovered right-button press; computes held as "this id currently owns capture and the left button is still down"; and sets clicked = true on release only if capture is still held by this id and the mouse is still over it (so dragging off a button before releasing does not count as a click). If opts.cursor/opts.tooltip are given and the region is hovered, it also sets the frame's cursor and registers a tooltip. Capture itself is released globally in ui.endFrame() whenever the left button is up.

Clipping

ui.pushClip(x, y, w, h) / ui.popClip() maintain a stack of logical-unit clip rectangles, each new push intersected with the current top of stack so nested clips can only shrink, never escape, their parent — then applies it as a real GPU scissor rect via the local setScissor helper, which converts to physical pixels using theme.scale (scissor rects are not affected by love.graphics.scale, so this conversion has to be done by hand). Clipping is used throughout for scroll views, text field interiors, and anywhere text/content must not bleed past a container's edge.

Scaling & logical units

All widget geometry is expressed in logical units matching the display's "design size" — the same numbers at any DPI or user-chosen UI scale (see Architecture: UI scale & DPI). Three small helpers bridge logical units to crisp physical pixels:

  • ui.snap(v) — floors a logical coordinate to the nearest whole physical pixel (floor(v * scale) / scale) before text is drawn, so glyphs never sit on a half-pixel boundary and blur.
  • ui.screenSize() returns the current logical window size (set every frame from ui.beginFrame(w, h)'s arguments, which App.draw computes from the physical framebuffer size divided by scale).
  • Fonts themselves are rasterized at the physical pixel density (via LÖVE's font "dpiscale" argument — see theme.lua's newFont) so text stays sharp while every measurement used by layout code stays in logical units throughout.

Scroll views

A vertical scroll view is a ui.beginScroll(id, x, y, w, h) / ui.endScroll(id, contentHeight) pair wrapped around content drawn at y - offset, where offset is the value beginScroll returns. Internally it keeps per-id state (y the current rendered offset, target the offset it's animating toward, contentH the last known content height) in scrollState. beginScroll clamps any stale offset against the content height known from last frame, then pushes a clip for the viewport. endScroll pops that clip, records this frame's real content height, and if the view is hovered and the mouse wheel moved, nudges target by wheelY * 60 clamped to the valid range; every frame y eases 45% of the remaining distance toward target (simple exponential smoothing, snapping once within 0.5px) — giving scrolling a soft, slightly springy feel rather than an instant jump. It also draws (and makes draggable, via another ui.region) a thin scrollbar thumb on the right edge whenever the content overflows. ui.scrollTo(id, y) / ui.scrollToEnd(id) let calling code jump a scroll view programmatically (e.g. after appending a chat message), and ui.scrollOffset(id) reads the current offset without drawing anything.

Text fields & focus

ui.focus holds the id of the text field currently receiving keyboard input (or nil). It changes only at frame boundaries: widgets request a change by writing to the module-local pendingFocus (ui.focusField(id, selectAll) requests focus, optionally also queuing a "select all text" flag consumed on the field's next draw; ui.blur() requests no focus by setting pendingFocus = false, a sentinel distinct from "no request" / nil) and ui.endFrame() applies it. Clicking anywhere that isn't the currently-focused field's own hit region also clears focus automatically (tracked via the per-frame flag ui._focusHitThisFrame, set by the field itself when it's the one being clicked).

ui.textField(id, x, y, w, text, opts) is a full single-line editor: caret and selection-anchor tracking (per-id state in fieldState), click-to-position and click-drag-to-select, double-click-to-select-word (wordLeft/wordRight walk UTF-8 codepoints classified by isWordChar), Shift-extend selection, Home/End, Ctrl+Left/Right (word jumps), Backspace/Delete (word-aware with Ctrl), Ctrl+A/C/X/V (the clipboard goes through love.system.getClipboardText/setClipboardText, and pasted text has newlines collapsed to spaces since this is a single-line field), Enter (reports submitted = true), Escape (blurs), and Tab (moves focus to the next/previous focusable field in this frame's draw order, unless opts.noTab or a custom opts.onTab(shift) handler is given — used to make Tab do something else, e.g. advance a wizard step). All text is handled as UTF-8 throughout (via Lua's utf8 library) so caret movement and selection respect multi-byte characters correctly. Other options: label (a floating label that moves above the border once the field has content or focus, Material-style), hint, prefix, error (shows a red message line below and tints the border), password (masks with •), maxLength, filter(str) (reject inserted text conditionally), autofocus, selectAllOnFocus. It returns (text, changed, submitted) — the caller is expected to store the returned text back into its own state (this is a controlled-component pattern, not an internally-owned value).

ui.dropdown(id, x, y, w, options, selected, opts) builds on the same per-id ui.state plus an ui.overlay popup list (itself a mini scroll view) that closes on outside click, right-click, or picking an option — note the pick is applied with a one-frame delay (st.hasPick/st.pick) because the popup is drawn in a later overlay pass than the dropdown's own return value for this frame has already been computed.

theme.lua: colors, fonts, icons

The header comment says it plainly: this "mirrors lib/app_theme.dart (Material 3 seeded from green, light and dark) plus the explicit colors the Flutter widgets use." Colors are plain {r, g, b, a} tables in the 0..1 range, built from hex strings by the local hex(s, a) helper (exposed as T.hex).

T.light / T.dark

Two full Material-3-style color role tables (primary, onPrimary, primaryContainer, secondaryContainer, surface, several surfaceContainer* tones, outline/outlineVariant, error, scrim, disabled, shadow, …), approximating tones generated from Flutter's Colors.green seed.

T.fixed

Colors that never change with the light/dark theme — the game table felt green, the title bar's fixed dark background, pure white/black, and a handful of named accent colors (orange, blue, red, green, cardBackBlue, missingBack, …) used for banners, warnings and card-back placeholders regardless of theme.

T.isDark / T.c / T.setDark(dark)

T.c is the active palette (T.light or T.dark), what almost all drawing code reads (theme.c.primary etc.); T.setDark flips T.isDark and repoints T.c. App re-derives theme.c from theme.isDark at the end of every draw rather than caching it, and screens with forceLightTheme can override theme.c = theme.light for the duration of their own draw.

T.alpha(c, a) / T.mix(a, b, t) / T.isLight(c)

Small color-math helpers: return a copy of a color with its alpha multiplied, linearly interpolate between two colors, and (via the WCAG relative-luminance formula) decide whether a color is "light" so UI code can choose black or white text/icon color for contrast on top of it (used e.g. by the color-picker preview button).

T.scale / T.setScale(s)

The global UI scale factor (DPI × user setting — computed in App.effectiveScale and applied here). T.setScale is a no-op if the scale hasn't actually changed; otherwise it updates T.scale and clears both font caches (fonts, iconFonts) since every cached font object was rasterized at the old pixel density and must be rebuilt.

T.font(size, weight) / T.iconFont(size)

Lazily creates and caches love.graphics.Font objects keyed by weight+size (weight one of "regular" (default), "medium", "bold", mapped to three bundled Roboto TTF files), always constructed with T.scale passed as LÖVE's font "dpiscale" argument so glyphs rasterize at full physical-pixel sharpness regardless of logical-unit size. Each text font also registers a fallback font, NotoSansSymbols2-Regular.ttf, for glyphs Roboto is missing (notably the card suit symbols ♠♥♦♣). T.iconFont separately caches MaterialIcons-Regular.ttf fonts by size.

T.icons / T.glyph(name)

T.icons is a lookup table from short semantic names (e.g. "delete_outline", "shuffle", "check_box") to Material Icons font codepoints — the comment notes that outlined variants used in the original Flutter code are mapped here to their filled counterparts (the bundled icon font apparently only ships filled glyphs). T.glyph(name) converts a codepoint to its UTF-8 character and caches the result, raising a Lua error for an unknown icon name (a deliberate fail-fast — a typo'd icon name is a programmer error, not something to silently swallow).

T.setColor(c, alphaMul)

Thin wrapper over love.graphics.setColor that also applies an optional extra alpha multiplier; aliased in ui.lua as ui.setColor and used throughout as the standard way to set the draw color from a theme color table.

widgets.lua: composite widgets

Small, screen-agnostic widgets built on top of ui.lua's primitives and shared by several screens, grouped under the local table W:

W.avatar(x, y, size, argb, source, showBorder)

Port of avatar_widget.dart: draws a player avatar as either a cover-fit image (looked up through image_cache.get by source.path or source.key) or, if no image is available, a flat square in the player's color (src/core/color.toRgba(argb) converts the app's packed ARGB integer representation to an {r,g,b,a} table). Unless showBorder == false, draws a border in the same player color (thicker at avatar sizes ≥100px).

W.banner(text, x, y, w, kind, onClick)

An orange ("warning", default) or blue (kind == "info") message banner that auto-sizes its height to the wrapped text, optionally clickable. Returns the height it drew, so callers can lay out whatever follows. This is what renders Home's "you were disconnected" message set by App.popToHome.

W.heading(text, x, y, opts)

A bold 14px (by default) section label; always returns 20 as the height to advance by.

W.card(x, y, w, h, opts)

A rounded, optionally bordered filled rectangle in the surface-container color — the generic "Material card" container background used under grouped content.

W.editorToolbar(x, y, w, title, actions)

Port of editor_toolbar.dart: a 56px-tall (W.editorToolbarHeight) in-body toolbar sitting just under the window's title bar, showing a screen title on the left and a row of icon-button actions ({icon, tooltip, onClick, id, disabled}) packed right-to-left from the end. Used by editor-style screens (deck editor, game-definition editor) for their own save/add/etc. actions, distinct from the app-wide title bar in src/app.lua.

W.tabBar(id, x, y, w, labels, selected)

Equal-width Material tab row (48px, W.tabBarHeight) with a primary-colored underline beneath the selected tab; returns (selectedIndex, height). Used by the game-definition editor's tabs (see Game Definition Editor).

W.chipWidth(label, selected, opts) / W.chip(label, x, y, selected, opts)

A 32px (W.chipHeight) Material filter chip: filled when selected, outlined otherwise, with a leading check icon when selected or a caller-supplied opts.icon otherwise. Returns (clicked, width).

W.flow(x, y, w, rowH, gap)

A tiny flow-layout helper: returns a place(width) function that hands back the next (x, y) for an item of the given width, wrapping to a new row (advancing by rowH + gap) once the current row would overflow w, plus a bottom() function returning the y just below the last row placed. Used wherever chips/buttons need to wrap, e.g. tag filter rows.

W.moveItem(list, from, to)

In-place reorder of a plain Lua array: removes the item at from and re-inserts it at index to (interpreted after the removal — see Reorder:finish below for how that index is computed from a drop position).

W.reorder(id) → Reorder object

Drag-to-reorder support for an immediate-mode vertical list. Usage is a three-step dance each frame: create the helper once per frame (local ro = W.reorder(id)), call ro:handle(i, hx, hy, rowY, rowH) once per row to draw a drag handle (grip icon) and record that row's current y/height, then once after the loop call ro:finish(x, w) which — while a drag is in progress — draws a ghost highlight over the dragged row and a drop-indicator line at the insertion point implied by the current mouse y, and on mouse release returns (from, to) (in W.moveItem index semantics) if the item actually moved, or nil otherwise. The drag only starts when the handle region itself is pressed (r.pressed and ui.mousePressed(1)), not from pressing anywhere in the row, so rows remain independently clickable elsewhere.

overlays.lua: dialogs, menus, toasts

While ui.lua provides the generic overlay/layer mechanism, overlays.lua (module table O) is the concrete implementation of the three overlay kinds the app actually uses, plus the app-shell integration point: src/app.lua's App.draw calls overlays.draw() once per frame (after the screen's own draw) to queue whatever's currently open, and overlays.keypressed(key) is consulted by App.keypressed ahead of the active screen (see Architecture: LÖVE forwarders). O.contentTop is set by App.draw to the title bar's height, so dialog scrims start below the title bar (keeping it visible/usable) the way a Flutter Navigator's dialog route would.

O.dialog(spec)

Opens a modal dialog described by a spec table — title, width (default 400), dark (use the fixed dark overlay panel color, for in-game dialogs drawn over the felt table rather than a screen), content(d, x, y, w) -> heightUsed (a custom-drawing callback), message (plain-text shortcut instead of/alongside content), actions (an array of {label, variant, onClick(d) -> keepOpen?, disabled}, right-aligned, where returning a truthy value from onClick keeps the dialog open — used for multi-step dialogs like the save-name overwrite confirmation), and onDismiss(d) called when closed via Escape or a scrim click. Returns the live dialog object, which gets a :close() method via metatable __index. Dialogs stack (pushed onto a local array) so one dialog can open another on top of it.

O.confirm(title, message, confirmLabel, onConfirm, opts) / O.alert(title, message, opts)

Convenience wrappers over O.dialog for the two most common shapes: a Cancel/Confirm pair (opts.danger renders the confirm button in the danger/red variant; opts.cancelLabel overrides "Cancel") and a single-OK informational alert.

O.closeDialog(d) / O.topDialog() / O.anyOpen()

Remove a specific dialog from the stack (blurring UI focus as it closes), peek the topmost dialog, and check whether any dialog or menu is currently open (consulted widely by screens/App to suppress input that shouldn't reach the table while something modal is up).

Internally, drawDialog(d, isTop) (called from an ui.overlay queued by O.draw) covers the whole screen below O.contentTop with a translucent scrim, sizes the dialog box to fit its title/content/actions (clamped to the available screen height, with content scrolling via ui.beginScroll/endScroll if it's taller than that), draws a soft shadow and rounded panel, the title, the scrollable content region, and the right-aligned action buttons. Only the top dialog closes itself on an outside click (and only if d.dismissible, default true, and no menu is currently open) — dialogs beneath it stay open and simply remain covered.

O.menu(x, y, items, opts) / O.closeMenus() / O.menuOpen() / O.menuItemRect(label)

Opens a context menu at a point. items is an array of {label, icon, onSelect, submenu, disabled, checked, divider} — submenu nests another items array, opened automatically on hover of its parent row (drawMenu recurses, pushing successive overlay layers so a submenu always draws above its parent and is itself dismissed correctly). divider = true draws a thin separator instead of a row. menuItemRect(label) exposes a currently-visible item's screen rect, used by scripted UI tests (see --script) to click a specific menu entry by label without hardcoding coordinates.

All context menus used throughout the game table — right-click on a card, a pile, a zone, a board widget — are built with O.menu; see Game Table Rendering for how each menu's item list is assembled, and CONTROLS.md's "Right-click menus" table for the user-facing behavior.

O.toast(text, seconds)

Queues a snackbar message shown at the bottom-center of the screen for seconds (default 4), fading out over the last quarter-second. Multiple toasts queue up but only the most recent is drawn at a time (drawToasts only renders toasts[#toasts], discarding expired ones each frame).

O.draw() / O.keypressed(key)

O.draw() is the per-frame integration point called from App.draw: queues one overlay per open dialog (checking the dialog is still in the stack before drawing it, in case an action closed it mid-queue), one overlay for the menu stack if any menu is open, and one overlay for toasts. O.keypressed(key) is the integration point called from App.keypressed: Escape closes the innermost open submenu first, else the top dismissible dialog (firing its onDismiss); Enter/Return triggers a dialog's onEnter(d) if it defined one; either way it returns whether any dialog or menu is open, so the caller knows whether to swallow the key from the underlying screen.

colorpicker.lua

Port of color_swatch_row.dart and color_picker_field.dart (module table P). Provides a reusable "pick a color" control used anywhere a player, board widget or similar needs a color assigned.

P.swatchRow(id, x, y, w, selected)

Lays out color.boardWidgetColorPalette (from core/color.lua) as a wrapping grid of 28px circular swatches (as many per row as fit in w), highlighting the selected one with a thicker blue ring. Returns (newSelected, heightUsed).

P.openPickerDialog(initial, onPicked)

Opens a full HSV picker dialog via overlays.dialog: a saturation/value square (rendered as a 24×24 grid of flat-colored rectangles — cheap enough per-frame without needing a shader), a hue bar below it (60 one-degree-wide strips), and a live color preview with its hex code, converting via core/color's rgbToHsv/hsvToRgb/hexFromColor. Dragging within the square sets saturation/value from the cursor position (clamped 0..1); dragging the hue bar sets hue (clamped to just under 1 so it doesn't wrap back to red). "Select" calls onPicked(argb) with the final color converted to the app's packed ARGB format.

P.field(id, x, y, w, selected, opts)

The composite control most screens actually use: the swatch row, a hex text field (editable, auto-synced whenever selected changes from outside), and a square preview/"more colors" button that opens the full picker dialog above. Typing a valid hex value updates the selection live via color.colorFromHex; picking from the full dialog is staged through per-id state (st.picked) and applied on the next call, the same one-frame-delay pattern ui.dropdown uses for its popup picks. Returns (newArgb, heightUsed).

filter_menu.lua

Ports of multi_select_filter_menu.dart and the CardSortMenu widget from card_sort_menu.dart (module table M) — two outlined "trigger button + popup" controls, differing in whether the popup stays open across picks (filters, since multiple can be toggled) or closes on the first pick (sort, single-select).

M.multiSelect(id, x, y, label, options, selected, excluded)

Trigger button shows label (N) where N is the current selected count. Its popup (opened/closed via per-id ui.state) lists every option as a checkbox row, flowing into multiple columns if there are more than MAX_PER_COLUMN (20) options, plus a "Select All"/"Deselect All" row at the top. selected and the optional excluded are plain id-keyed set tables ({[id] = true}) mutated in place — the function has no meaningful return value for them; callers read the same tables back after the call. When excluded is provided, each row also gets a small secondary toggle (a "stop excluding" / "exclude" icon button) that marks an option as actively excluded rather than merely unselected — this powers the Card Library/deck editor's "exclude cards with this tag" filter behavior documented alongside core/card_filters.lua. Selecting an option clears its exclusion and vice versa. The popup closes on an outside click (checked with ui.hoverIgnoringLayer against both the popup panel and the trigger button itself, so re-clicking the trigger toggles rather than reopening instantly).

M.sortMenu(id, x, y, options, selectedId)

Trigger button shows "Sort" or "Sort: <name>"; its popup is a plain single-select list (prefixed with a synthetic "Default order" entry whose id is nil) that closes immediately on pick, again via the one-frame-delayed st.hasPick/st.pick pattern. Returns (selectedId, triggerWidth).

M.triggerWidth(label) / M.close(id)

Measures a trigger button's width without drawing it (for layout pre-computation, as card_filter_bar.lua does), and force-closes a specific menu's popup by id.

card_filter_bar.lua

The shared filter/sort/search UI strip (module table B) used by every screen that shows a filterable list of card definitions — the Deck Editor's card pool and the game table's Card Library overlay — so that both present and behave identically. All of the actual filtering/sorting logic it drives lives in src/core/card_filters.lua; this module is purely the UI shell around it.

B.newState(game) / B.clear(st, game)

Builds (or resets) the filter state table for a given game definition: a selected and excluded set per tag group (keyed by game.tagGroups[i].id), a sets set, and an empty search query. A freshly-created state is "fully permissive" — nothing filters anything out. B.clear resets only the Set/tag-group filters, deliberately leaving sortKey and query untouched (a "Clear Filters" action shouldn't also clear what you were searching for or how you sorted).

B.visible(st, game)

Returns the game's cards filtered by core.card_filters.cardMatchesFilters against the current state and then sorted by core.card_filters.sortCardDefinitions according to st.sortKey — the single function screens call each frame to get "what should I actually draw right now".

B.isFiltered(st)

True if any Set or tag-group filter is active (selected or excluded) — note search text and sort choice do not count, matching B.clear's scope. Used to decide whether to show a "Clear Filters" affordance at all.

B.drawFilters(prefix, st, game, x, y, w, opts)

Draws nothing at all for a game with no sets, no non-empty tag groups, and no caller-supplied opts.leading buttons. Otherwise draws (depending on opts.compact) either a full-width "Clear Filters" button above a wrapping row of filter trigger buttons, or a single compact row — optional leading buttons first (opts.leading = {{label, icon, id, onClick, variant}}, e.g. the Card Library's "Open Library" style actions), then a Set (N) multi-select (only if the game defines sets, counting how many cards belong to each set for the popup labels) via filter_menu.multiSelect, then one multi-select per non-empty tag group, then a Sort trigger (filter_menu.sortMenu, offering "Set" and "Name (A-Z)" plus one entry per tag group) — and in compact mode, a trailing "Clear Filters" button that only appears once B.isFiltered is true. Uses widgets.lua's W.flow-style manual wrapping (reimplemented locally as the place(width) closure) to wrap buttons onto new rows as needed. Returns the y coordinate just below everything drawn.

B.drawSearch(prefix, st, x, y, w, opts)

A labelled search text field ("Search by name or ID") with a clear ("×") button that appears only once there's text to clear. Returns the y just below it. Kept separate from B.drawFilters so callers can place search above or below (or interleaved with) the filter row as their layout needs.

save_name_dialog.lua

Shared port of save_game_dialog.dart and save_deck_dialog.dart (module table D) — the "give this a name" prompt used both for saving a practice game and for saving a deck, unified into one dialog builder since the two flows are otherwise identical in shape.

D.open(spec)

spec fields: title, fieldLabel, emptyNameMessage (validation error text for a blank name), existing (an array of {name, trailing} — or a function returning one, evaluated once up front — rendered as a tap-to-reuse list below the name field, trailing typically a timestamp), existingHint/emptyListText (captions for that list), exists(name) -> bool (called on submit to decide whether to show an overwrite step), overwriteTitle/overwriteMessage(name), onSave(name) (called once the name is finally confirmed, whether fresh or overwritten), and an optional footer(x, y, w)/footerH for extra caller-supplied content under the list (reserved space subtracted from the list's own height).

Internally it's a single overlays.dialog whose content function switches entirely based on local state st.confirming: normally it shows the name field (validated through deck_library.validateName on submit — note this generic name-validity check is reused even for saving a practice game, not just decks) and the reusable-name list; once spec.exists(name) returns true on submit, it flips into a one-screen confirmation showing spec.overwriteMessage(name) instead, and relabels the dialog's own title and its primary action button ("Save" → "Overwrite") by mutating d.title and d.actions[2].label from inside the content callback — an example of a dialog spec reaching back into its own live object to adapt itself after the fact, rather than being fully declarative up front. Pressing the text field's Enter key, picking a name from the list and clicking "Save", or clicking an existing-name row all funnel through the same local submit() function so the validation/overwrite logic only exists once.
