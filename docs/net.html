Two hosting modes

Cardflux can get a group of players into the same game in two different ways, and almost everything in this folder exists to serve one or the other:

  • Direct peer hosting. One player's client becomes the host: host_server.lua binds a TCP port directly (optionally forwarded through the LAN gateway by upnp.lua) and the other players' clients connect to it with game_client.lua. There is no account system and no central authority — whoever is hosting is the server for that one game, using the same Session / HostEngine code a client would use if it were playing solo.
  • Dedicated lobby server. Players instead point game_client.lua at a long-running Cardflux Server (Go) process. The server answers the initial handshake with serverInfo instead of welcome, which makes game_client.lua hand the connection off to server_client.lua — a richer client that understands accounts, chat, rooms, decks and admin requests, documented end-to-end on Multiplayer Lobby Screens.

Both modes speak the exact same line-based JSON protocol defined in protocol.lua, and both ultimately feed the same in-game message types (gameData, fullState, etc.) into src/game/session.lua. The lobby server additionally runs an embedded copy of the client's own rules engine so it can referee a game authoritatively — see Why Go embeds a Lua engine on the server page.

protocol.lua — wire format

src/net/protocol.lua
Defines the one-JSON-object-per-line wire format and the non-blocking Connection wrapper around a LuaSocket TCP socket. A direct Lua port of the Flutter app's lib/networking/net_message.dart, kept byte-compatible so a LÖVE client and the (now retired) Flutter client could interoperate.

Every message on the wire is a single line of JSON: {"type": "<name>", "payload": {...}}, newline-terminated. P.encodeLine(msgType, payload) builds that line; P.decodeLine(line) parses it back into { type, payload } or nil for anything malformed or blank.

P.defaultGamePort = 51234

The TCP port a direct-hosted game listens on by default (overridable per-host).

P.serverProtocolVersion = 1

Sent as payload.serverProtocol in every hello message. A direct peer host ignores this field entirely, but a Cardflux lobby server compares it against its own ProtocolVersion constant (see internal/server/server.go) and refuses the connection outright if they don't match. This is the one hard compatibility contract between the Lua client and the Go server — the comment right above this constant says to bump it and run server/tools/sync-engine.ps1 whenever the server protocol changes, which also re-syncs the mirrored rules engine (see the engine mirror).

P.heartbeatInterval = 4   P.heartbeatTimeout = 12

Every connected party pings every 4 seconds; if no data at all (not just pongs) has arrived for 12 seconds the connection is dropped as dead. The same two constants are reused identically by host_server.lua, game_client.lua and server_client.lua.

Connection

A thin stateful wrapper created by P.wrap(sock) (sets the socket non-blocking and enables TCP_NODELAY). It owns an output queue and partial-read input buffer so callers never have to think about partial sends/receives:

Connection:send(msgType, payload)

Encodes one message, queues it, and calls :flush().

Connection:sendRaw(line)

Queues an already-encoded line — used by host_server.lua:broadcast() so a message is encoded once and reused for every client.

Connection:flush()

Writes as much of the queue as the socket will currently accept; resumes mid-message next call if the socket was not ready for all of it.

Connection:poll()

Returns every complete line received since the last call, as decoded {type, payload} messages, plus a second boolean saying whether any bytes arrived (used to reset heartbeat-timeout clocks even for malformed lines).

Connection:close() / Connection:closeAfterFlush()

The latter blocks briefly (0.5s) to best-effort flush a final message — typically a disconnect with a reason — before tearing the socket down.

Connection:pendingBytes()

Bytes still queued to send; used by upload/progress UIs to show backpressure.

Non-blocking connect

P.connect(host, port, timeoutSeconds) -> connector

Starts a non-blocking connect() and returns an object with connector.poll(), which must be called every frame until it returns something other than "pending": either "connected", conn (a wrapped Connection) or "failed", message. Used by both game_client.lua (joining) and indirectly by the asset workers' raw socket connects.

Background loop

A tiny global registry so objects that need per-frame network servicing don't each need their own hook into love.update. src/app.lua calls P.updateAll(dt) every frame regardless of which screen is active, which is what lets a game continue running in the background while the player browses other screens, and P.stopAll() on quit.

P.register(obj) / P.unregister(obj)

obj just needs an :update() method; HostServer, GameClient, ServerClient and the asset-sync/upload Job objects all register themselves.

P.updateAll(dt) / P.stopAll()

Drives every registered object's :update() each frame, or calls each one's optional :stop() and clears the registry on app shutdown.

netinfo.lua — local/public IP discovery

src/net/netinfo.lua
Port of lib/networking/network_info.dart. Figures out the addresses other players would need to type in to reach a directly-hosted game.
N.localIPv4Addresses() -> { ip, ... }

Best-effort enumeration of this machine's non-loopback IPv4 addresses without native interface enumeration: it opens a UDP socket, "connects" it to 8.8.8.8:53 (which sends no packet, just makes the OS pick an outbound route) and reads back the local address that route would use, then adds every address the local hostname resolves to via socket.dns.

N.fetchPublicIPv4(onDone)

Fetches this machine's public IP from api.ipify.org on a LÖVE worker thread (plain HTTP — LuaSocket has no TLS in this build, but the response contains nothing sensitive, just your own IP) and delivers it back to the main thread through N.update(), which must be polled every frame. Used by the Multiplayer screen to show the address a friend over the internet should connect to.

upnp.lua & upnp_worker.lua — automatic port forwarding

src/net/upnp.lua
Port of lib/networking/upnp_port_mapper.dart: best-effort automatic router port forwarding via UPnP IGD, so hosting for internet players doesn't require manually configuring the router.

UPnP IGD port mapping is a two-phase dance — SSDP multicast discovery to find a gateway, then a SOAP HTTP call to actually add or remove a mapping — and both phases involve several seconds of network waiting, so the whole thing runs on a worker thread (upnp_worker.lua) spawned per request; upnp.lua itself only exposes a tiny main-thread API and never blocks the UI. Every failure mode (no gateway found, gateway refused, timeout) collapses to the same "not mapped" outcome rather than surfacing an error, because UPnP is always an optional convenience — LAN play works with or without it.

U.requestMapping(port, onDone, description)

Spawns a worker to SSDP-discover a gateway, find its WANIPConnection/WANPPPConnection service, and SOAP-call AddPortMapping for TCP port. onDone(mapping) is called with a reusable mapping table on success or nil on any failure. Called by host_server.lua:start() immediately after it binds its listening socket.

U.releaseMapping(mapping)

Fire-and-forget DeletePortMapping for a mapping requestMapping created. Called by host_server.lua:stop().

U.update()

Must be polled every frame (from src/app.lua's App.update) to collect worker results and invoke the matching onDone callback.

upnp.lua also exposes its lower-level parsing/building helpers as module functions — parseLocation, splitUrl, resolveUrl, findControlUrl, soapEnvelope, addFields, deleteFields — purely so upnp_worker.lua (running in a separate Lua state on its own thread) can require the same module and reuse them; none of this parsing logic is duplicated between the main-thread module and the worker.

src/net/upnp_worker.lua
The actual thread body passed to love.thread.newThread. Receives (job, out) where job is {op="add"|"delete", port, description?, controlUrl?, serviceType?} and out is a love.thread.Channel it pushes exactly one result table onto.

For an "add" job it SSDP-searches for 3 seconds, collecting every distinct LOCATION it sees (because printers and smart TVs answer SSDP too, not just routers), fetches each device's description XML, and scans it with U.findControlUrl for a WAN connection service, scoped to the matching <service> block so an unrelated service's controlURL can never be picked up by mistake. It also has to work out which local address the gateway should forward to (localAddressFor), again using the "connect a UDP socket, read back the route" trick from netinfo.lua. A SOAP fault (HTTP 500) is treated purely by status code — the body isn't parsed. A "delete" job just re-issues the SOAP call with DeletePortMapping.

host_server.lua — direct-hosting the lobby

src/net/host_server.lua
Port of lib/networking/host_server.dart. Accepts incoming TCP connections, runs the hello/welcome handshake, keeps the roster of connected players, heartbeats and times out dead connections, and can kick someone.

This is the "server" side of direct peer hosting — it has no concept of accounts, only of the single game it is hosting for this run. H.new() creates an instance; the owning screen (the practice/host flow under Multiplayer) sets two optional callbacks before/while running:

  • onIncoming(senderId, msg) — every message that isn't part of the handshake or a ping, handed to HostEngine to apply to the authoritative game state.
  • onRoster(roster) — fires whenever a player joins or leaves.
  • reclaimableIdCheck(id) — set once a game is actually in progress; when present, a hello must present a rejoinPlayerId that this predicate accepts (i.e. a previously disconnected seat) or the connection is refused with seatUnavailable. This is what lets a player reconnect into their own seat after a dropped connection but blocks a stranger from taking an empty seat mid-game.
H:start(hostPlayer, maxPlayers, hostAvatarBytes, port) -> port | nil, err

Binds socket.bind("*", port or P.defaultGamePort) in non-blocking mode, registers itself on the protocol loop, and kicks off a best-effort upnp.requestMapping for the bound port (set self.noUpnp to skip it — used by tests). Hosting itself never waits on the UPnP result.

H:update()

Called every frame via the protocol loop. Accepts new sockets (refusing them outright once maxPlayers - 1 clients are already connected, since one seat is the host itself), reads pending (not-yet-said-hello) connections and times them out after heartbeatTimeout, then for every established client: polls for messages, answers ping with pong, routes everything else to onIncoming, and enforces the heartbeat timeout / sends its own pings.

H:handleHello(conn, msg)

Validates capacity and (if set) reclaimableIdCheck, resolves a free player color via H:resolveColor (preferring the client's requested color, falling back to color.boardWidgetColorPalette), decodes a base64 avatar if one was sent, assigns a UUID (or reuses the reclaimed one), replies with welcome, and broadcasts the updated roster.

H:roster()

The host plus every connected client as models.PlayerInfo, reordered to match H:setSeatOrder(ids) when one has been set (used once a game has started and seats are fixed).

H:kick(id)

Sends a disconnect with reason "kicked", flush-closes, and removes the client.

H:broadcast(msgType, payload, exceptId)

Encodes once via P.encodeLine and fans the same raw line out to every client (optionally skipping one) — the efficient path for frequent state broadcasts.

H:stop(reason)

Optionally broadcasts a final disconnect, flush-closes every connection, closes the listening socket, releases the UPnP mapping, unregisters from the protocol loop, and calls onStopped.

This module sits directly underneath src/game/host_engine.lua: HostEngine owns a HostServer instance and is where onIncoming actually gets wired up to mutate and rebroadcast game state.

game_client.lua — joining a peer host or a server

src/net/game_client.lua
Port of lib/networking/game_client.dart. The single entry point used to join either kind of remote: a direct peer host or a Cardflux lobby server — the caller doesn't need to know which until the handshake resolves.

Status machine: "idle" → "connecting" → "connected" | "failed" | "server", then eventually "disconnected". The key branch is in C:update() once the handshake's reply arrives: if the remote answers with serverInfo (meaning it's a Cardflux server, not a peer), the client stops treating itself as a GameClient — it sets status "server" and the caller is expected to hand the now-adopted connection to server_client.lua (S.adopt) instead. If it answers with welcome, this is the in-game connection and stays one for the rest of the session.

C:connect(host, port, name, color, avatarBytes, rejoinPlayerId)

Starts a non-blocking P.connect and remembers the hello payload to send once the socket is up.

C:update()

Drives the connector to completion, then sends hello (including serverProtocol = P.serverProtocolVersion so a real server can validate it immediately), then polls for messages each frame: answers pings, branches on serverInfo/welcome/disconnect, and for everything else caches the latest lobbyRosterUpdate / gameData / fullState (so a screen that starts observing mid-game can immediately replay the last known state) before invoking onMessage.

Once connected to a peer host, this is the client-side counterpart to host_server.lua and feeds src/game/session.lua (the ClientGame side of the shared session code).

server_client.lua — the lobby-server protocol client

src/net/server_client.lua
The full-featured client for a Cardflux lobby server connection: accounts, the lobby roster, chat, rooms, decks/collections, trading and admin requests, all multiplexed over one TCP connection that game_client.lua handed off after the handshake.

Every lobby screen under src/ui/screens/server/ reads this object's fields directly each frame — info, self, users, rooms, games, chat, room/roomId, roomChat, trade — in keeping with the app's immediate-mode UI style (see UI Toolkit): there's no separate event-driven view-model, the fields are the state, mutated as server push messages arrive in S:handle(m).

Request/response multiplexing

S:request(msgType, payload, onResponse) -> rid

Stamps the payload with an auto-incrementing rid, remembers onResponse keyed by that id, and sends it. Every request-style call in the codebase (sign-in, create room, admin actions, trade offers...) goes through this. The server always answers with a type = "response" message carrying the same rid, matched back up in S:handle. If the connection drops, every still-pending callback is immediately invoked with {ok = false, error = "disconnected", ...} so UI code never hangs waiting forever for a reply that will never come.

Password hashing & remembered sessions

S.passwordHash(email, password) -> hex string

SHA-256 of "cardflux:" .. normalizedEmail .. ":" .. password, computed client-side because the connection itself is unencrypted plain TCP (see Security on the server page); the server then bcrypts this hash for storage, so the real password is never transmitted and the stored hash is never useful on its own for logging in elsewhere.

S.savedSession / S.saveSession / S.forgetSession / S.clearSession(key)

Per-server ("host:port") "Remember me" persistence via src/data/settings.lua, under the key server_sessions. forgetSession drops the token but keeps the remembered email (for sign-out-but-prefill); clearSession drops everything.

The game channel

S:gameChannel() -> channel

Returns a small shim object presenting the same shape ClientGame expects from a direct game_client.lua (:send, .status, .onMessage/.onStatus, cached lastGameData/lastFullState) — but backed by this shared server connection instead of its own socket. GAME_TYPES is the set of message types (gameData, fullState, drag-preview messages) that get routed to this channel rather than treated as lobby traffic in S:handle. This is the mechanism that lets the in-game screen reuse exactly the same client game code whether you're playing via a peer host or inside a server-hosted room.

Message handling

S:handle(m) is a large dispatch over message type, each branch updating the relevant field(s) and calling S:emit(event, ...) for any screen that registered a listener with S:on(event, fn). Notable branches: lobbyState (the initial full snapshot after sign-in), tokens/newToken (collection-mode currency and session-token rotation), tradeInvite/trade/tradeClosed (see the Trade screen), serverShutdown (pops a live countdown alert via overlays), and roomClosed.

S:avatarKey(hash) / S:avatarKeysByUserId()

Lazily fetches a user's avatar image the first time it's referenced (one avatarGet request per distinct hash, cached forever in self.avatarKeys) and hands back an image_cache key once loaded — used directly by the table screen to draw opponents' avatars in a server-hosted game.

admin_file_manager.lua — admin file browsing/upload

src/net/admin_file_manager.lua
Backs the admin "Files" tab: list and delete a game's files on the server over the normal request/response channel; upload streams over a second, dedicated connection on a worker thread so a large file never blocks the UI thread's networking.
M.list(sc, gameId, path, onDone) / M.delete(sc, gameId, path, onDone)

Plain adminFileList/adminFileDelete requests via server_client.lua.

M.upload(sc, gameId, destPath, localPath, onProgress, onDone)

Looks up the local file's size (via a directory listing rather than reading it — see localFileSize), then spawns admin_upload_worker.lua on a thread, passing it the host, port, auth token, target game id and destination path. The returned Job object registers itself on the protocol loop and polls a love.thread.Channel for progress/done/error messages pushed by the worker, translating them into the onProgress(bytesSent, totalBytes) / onDone(err) callbacks the admin screen uses.

The same Job shape (update/finish, polling a channel, registering on the protocol loop) is reused almost verbatim by asset_sync.lua's download jobs — both are "a worker thread streams a file over its own connection, the main thread just watches a channel."

admin_game_manager.lua — install/remove games

src/net/admin_game_manager.lua
Backs the admin "Games" tab's Remove Game and Upload New Game actions.
M.remove(sc, gameId, onDone)

Plain adminGameDelete request.

M.installFromZip(sc, zipPath, onProgress, onDone)

First validates the zip entirely locally via validateZip — extracts it to a throwaway temp folder using the Windows-provided tar.exe (via src/platform/winproc.lua), checks it contains exactly one top-level folder containing a gamedef.json whose id matches that folder's name — so a malformed upload never wastes time going over the wire. It then reuses admin_file_manager.lua's upload machinery to push the zip into the server's flat staging area (passing gameId = "", a special case the server's asset channel recognizes — see assets.go), and finally sends an adminGameInstall request naming the uploaded file so the server unpacks and registers it as a real game.

Zip validation via tar.exe is Windows-only; validateZip returns an explicit "not supported on this platform yet" error elsewhere.

admin_upload_worker.lua — upload thread body

src/net/admin_upload_worker.lua
The LÖVE thread body admin_file_manager.lua starts for one upload. Opens its own TCP connection, authenticates with assetHello, then streams the file in 192 KB (CHUNK) base64-encoded assetPut messages, each acknowledged with assetPutAck before the next chunk is sent — simple flow control without needing TCP-level backpressure introspection.

192 KB is called out in the source as matching the server's own assetChunk constant (see assets.go) — the two sides agree on a chunk size even though nothing in the protocol strictly requires it. Progress is reported after every acknowledged chunk via out:push({kind="progress", bytes=offset}); a thrown Lua error anywhere in the pcall'd body becomes an {kind="error", message=...} push instead of crashing the thread silently.

asset_sync.lua — game asset caching

src/net/asset_sync.lua
Keeps a local, on-disk mirror of one server-hosted game's files (gamedef.json, set images, built-in decks) under <save dir>/servers/<host_port>/games/<gameId>/, laid out identically to a local game-library folder so game_loader.lua and image_resolver.lua can consume it completely unchanged.

Sync is manifest-driven and content-addressed: the server reports every file's path and SHA-256 (gameManifest request); a local .cardflux_manifest.json index (read/written by readIndex/writeIndex) records the hash of each file already downloaded, and only files whose hash differs (or that are simply missing) get queued for download. Files the server no longer lists are deleted locally too, so the cache can't drift from the server's current content.

A.ensureGame(sc, gameId, onDone, onProgress)

The main entry point. Memoizes a fully-loaded game object per gameId keyed by manifest hash (sc.loadedGames) so re-entering an already-current game is instant and network-free. Otherwise it diffs the manifest against the local index and, if anything is missing or stale, spawns asset_worker.lua on a thread to fetch just the delta, reporting onProgress(done, total, bytes, reused) as files land. Once complete it calls resolver.clearCache() and reloads the folder with game_loader.loadFromFolder.

A.cachedGame(sc, gameId)

Returns an already-memoized game with no network activity at all, or nil.

One subtlety worth calling out: serverRoots() enumerates not just this save directory's own servers/ folder but sibling identity folders too (the --identity dev flag documented on the architecture page, used to run a second instance as a different player on the same machine) — so running two instances for testing doesn't require downloading the same game assets twice.

asset_worker.lua — download thread body

src/net/asset_worker.lua
The thread body asset_sync.lua starts to actually fetch a game's missing/changed files. Its most interesting job is avoiding redundant downloads entirely by reusing bytes already present somewhere on disk.

Before downloading anything, sourceFolders() builds a list of every place on this machine a byte-identical copy of a wanted file might already live: the destination cache folder itself, any local game library folder whose gamedef.json reports the same game id (localGameFolders() — so if you already have the game installed locally, joining the same game on a server reuses those files instead of re-downloading them), and the equivalent cache folder under every other server this machine has connected to (job.serverRoots, passed in from asset_sync.lua). reuseLocal(f, dest, sources) checks size as a cheap pre-filter then verifies a true SHA-256 match before copying — never trusting a filename or size alone.

Only files that can't be found anywhere locally actually open a second TCP connection to the server's asset channel (connect()/download(), same assetHello → assetGet → streamed assetData chunks protocol as the upload worker's chunked assetPut, just in the opposite direction) and get written to disk. Every file, reused or downloaded, is reported back to the main thread as {kind="file", path, sha256, bytes, reused} so asset_sync.lua can update its manifest index and progress UI incrementally rather than only at the very end.
