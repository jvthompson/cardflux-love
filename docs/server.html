Why Go embeds a Lua engine

The single most distinctive design decision in this codebase: the Go server does not reimplement CardTable's card-game rules. Instead, it runs a byte-for-byte copy of the LÖVE client's own Lua rules code — lib/json.lua, every file in src/core/, and src/game/session.lua + src/game/host_engine.lua — inside an embedded Lua interpreter (gopher-lua, a pure-Go Lua 5.1 VM). These files are vendored into server/engine/ by server/tools/sync-engine.ps1 and compiled straight into the server binary via //go:embed.

The payoff is that a server-hosted game is refereed by exactly the same code that would run if one player directly hosted for their friends (see the two hosting modes on the Networking page) — every card-movement rule, every zone constraint, every pack-opening algorithm lives in one place and one place only. There is no second, Go-flavored implementation of the rules that could silently drift from the Lua one. The cost is the small Go↔Lua bridge described below, and a build-time discipline: the comment at the top of sync-engine.ps1 literally says to run it after any change to those client files, and internal/server/version_test.go fails the test suite if the vendored copy's recorded protocol version doesn't match the server's.

cmd/cardflux-server/main.go — entrypoint

server/cmd/cardflux-server/main.go
Command-line entrypoint: parses flags, opens the data directory, builds the game library, and starts Server.Serve.

Flags: --data (default data) and --port (default 51234 — the same default as the client's P.defaultGamePort). It creates <data>/games/ if missing, opens server.log for append (logging to both the file and stdout via io.MultiWriter), opens the SQLite store, builds a games.Library seeded with one built-in game (the embedded standard_52 deck read from EngineFS), scans it, and logs a one-line summary per game (card count, file count, starter deck count). var build = "dev" is overwritten at build time via -ldflags -X main.build=N by tools/build.ps1, so a release binary always logs its exact build number on the first startup line. SIGINT/SIGTERM trigger a graceful srv.Close() (see shutdown.go).

embed.go — embedding the engine files

server/embed.go
Three lines: a package-level //go:embed engine directive that bakes the entire server/engine/ directory tree into the compiled binary as cardflux.EngineFS.

This is what lets the server ship as a single self-contained executable with no external Lua files to distribute or go missing — the rules engine, the built-in standard deck JSON, and a recorded protocol-version marker are all inside the binary.

internal/engine/engine.go — the gopher-lua bridge

server/internal/engine/engine.go
Package engine: the only Go code that actually talks to Lua. Wraps one gopher-lua state (VM) per running game (Room), running the embedded room.lua shim.

Every value that crosses the Go↔Lua boundary is a JSON string — Go never inspects or builds a Lua table directly, and Lua never needs to understand a Go struct. This keeps the bridge tiny and means the engine package's Go-side API is just a handful of methods taking/returning strings:

type Sink interface { SendTo(id, msgType, payload string); Broadcast(msgType, payload, exceptID string) }

Implemented by Room (see rooms.go) — how the Lua side delivers outgoing messages back out to real network connections. Lua calls the globals __send and __broadcast (installed as closures over a Sink in newVM), which simply forward to this interface.

newVM(sink Sink) (*VM, error)

Creates a fresh lua.LState with an enlarged registry (RegistrySize: 20480, growable to 8 MiB) — the comment notes lib/json.lua builds large documents like a full gameData payload with table.concat over many small pushes, which needs headroom beyond gopher-lua's default stack size. It installs three globals (installRequire, __now, __send/__broadcast), then loads and runs the embedded room.lua string, capturing the table it returns as vm.room — this table's fields are the actual entry points (start, roster, message, etc.) that vm.call(name, args...) invokes.

installRequire(L *lua.LState)

Replaces Lua's global require with a closure that maps a dotted module name ("src.core.models") onto an embedded file path (engine/src/core/models.lua), reads it out of cardflux.EngineFS, compiles and runs it, and memoizes the result — functionally identical to what LÖVE's own require does for the client, just reimplemented against the embedded filesystem instead of love.filesystem. This is the mechanism that lets room.lua (and transitively src/game/session.lua/host_engine.lua) require the exact same module names the client uses, unmodified.

Room: the per-game handle

StartRoom(sink Sink, gameJSON, playersJSON, sharedJSON string) (*Room, error)

Creates a VM and calls room.lua's start — this is what turns a server Room (see rooms.go) from a lobby waiting-list entry into a live game.

(*Room) Roster(connectedJSON string) error

Tells the engine which seated players currently have a live connection (as a JSON array of ids), so it knows whom it can actually message.

(*Room) Message(playerID, line string) error

Delivers one raw client line (the exact {"type",...,"payload",...} JSON text, unparsed by Go) as if that player had sent it directly to a host_server.lua-style host.

(*Room) AddSpectator(id) / RemoveSpectator(id)

Adds/removes a read-only observer.

(*Room) Tick() error

Advances timers (e.g. the fading drawn-arrow widget) — called on a fixed schedule by the owning Room's goroutine, not by player messages.

OpenPack(cardsJSON, settingsJSON string) (string, error)

A one-shot, roomless VM invocation that runs the exact same pack-opening algorithm as the client's Pack Generator widget (src/core/pack_generator.lua), used by collection-mode pack purchases (decks.go's handlePackBuy) so server-sold packs use identical odds to a locally-hosted game's widget.

The engine mirror & room.lua

server/engine/ holds the vendored client files plus two server-only additions:

  • server/engine/builtin/standard_52.json — a copy of the client's built-in standard 52-card deck definition, so a server can offer that game out of the box with zero files on disk.
  • server/internal/engine/room.lua (embedded via //go:embed room.lua right in engine.go, not under server/engine/) — the shim that makes the client's HostEngine and Session runnable headless inside Go. It constructs a fake "host" object (shim) exposing :roster(), :sendTo, :broadcast — the same shape src/net/host_server.lua presents to HostEngine on the client — but wired to the Go-provided __send/__broadcast globals instead of real sockets. HostEngine itself never knows it's running inside a Go process.

room.lua exposes exactly the functions engine.go's Room methods call: R.start (builds a GameDefinition, adds the generated 52 standard cards if any zone wants a standard deck — mirroring game_loader.lua's own logic — then calls Session.dealFromZones and HostEngine.new), R.roster, R.message, R.addSpectator/R.removeSpectator (spectators are filtered through state_filter.lua so they never see hidden information, even one who also holds a seat — note the specID prefix trick in rooms.go that gives a spectating seat-holder a distinct engine identity from their own seat), R.tick, and R.openPack.

internal/server/server.go — connection lifecycle

server/internal/server/server.go
The Server type: top-level state (clients, rooms, trades, settings) and the accept loop. Also where ProtocolVersion lives.
const ProtocolVersion = 1

Must equal serverProtocolVersion in the client's src/net/protocol.lua. This is the one hard version gate between client and server: handleConn (below) refuses any client whose hello.serverProtocol doesn't match, with reason versionMismatch — rather than attempt best-effort compatibility across protocol revisions.

(*Server) Serve(ln net.Listener) error

Starts the background allowanceLoop (see lobby.go) then accepts connections forever, handing each to go s.handleConn(proto.Wrap(nc)) — one goroutine per TCP connection.

(*Server) handleConn(conn *proto.Conn)

Reads exactly one first message to decide what kind of connection this is, mirroring the client's own dual-purpose dial logic: a "hello" starts an authenticated lobby Client session (after checking protocol version and whether the server is shutting down, then replying with serverInfo — the message that makes game_client.lua recognize this as a server rather than a peer host); an "assetHello" instead hands the raw connection to s.serveAssets (assets.go) for file transfer. A pre-protocol client (one whose serverProtocol field is absent/zero — i.e. too old to know servers exist) is closed with serverRequiresUpdate rather than a version-mismatch message it wouldn't understand.

Client & request dispatch

Each connected Client runs c.run() in its own goroutine: a tight loop of conn.Read() → c.handle(m). handle looks up the message type across three ordered handler maps populated by init() functions scattered across every other file in this package (publicHandlers → no login required, e.g. register/login; authedHandlers → must be signed in; adminHandlers → must be signed in and IsAdmin) — and if the message type matches none of them, treats it as raw game traffic and calls c.forwardToRoom(m) (defined in rooms.go). This Go-side dispatch table mirrors the client's own habit of routing "everything I don't specifically recognize" straight through to the game engine.

Every request/response exchange follows the same shape: the client payload carries an opaque rid (round-trip id, see server_client.lua's request/response multiplexing), and c.reply(rid, data) / c.fail(rid, code, message) echo it back inside a type: "response" message with ok: true/false.

Login rate limiting

A small in-memory limiter tracks failed sign-in attempts per key (both "ip:<addr>" and "email:<address>" are checked, so a distributed attack against one email from many IPs is still caught). After 5 failures the wait doubles each additional failure, from 30 seconds up to 30×2⁵ seconds, capped by the min(e.fails-5, 5) shift. A successful login clears both keys.

auth.go — accounts & sessions

server/internal/server/auth.go
Registration, login, session resume, profile updates, avatar fetch. Handlers: register, login, resume (public); logout, profileUpdate, avatarGet (authed).

Passwords never reach the server in the clear: the client hashes with server_client.lua's S.passwordHash (SHA-256 of a fixed string template) before sending, and the server bcrypts that hash for storage (validPassHash just checks it's a well-formed 64-hex-char SHA-256 digest). register additionally validates email format, enforces ValidName (1–24 printable characters, no leading __ — that prefix is reserved, matching how rooms.go's specID mangles spectator ids and SERVER_ID in room.lua uses __server__), decodes and validates an optional avatar (must be a real PNG — checked by magic-byte signature — under 512 KB), and respects the server's registrationOpen setting (always allowing exactly the very first account, so there is always a way to bootstrap an admin).

CreateUser in the store makes the first account ever created an admin automatically (count == 0 check inside the same transaction) — this is the server's entire admin-bootstrapping mechanism, matching the behavior documented in server/README.md.

authenticateWithToken is the shared tail of register/login/resume: it refuses a disabled account or a server mid-shutdown, grants a collection-mode token allowance if a new day/week has started since the last grant, and — notably — if the same account is already connected elsewhere, it evicts the older connection (CloseWith("loggedInElsewhere")) rather than refusing the new one, enforcing "one active connection per account" without a separate presence check.

lobby.go — roster, chat, game list

server/internal/server/lobby.go
The shared lobby snapshot (lobbyState, sent once right after sign-in) plus ongoing broadcasts (users, rooms, serverInfo) and lobby/room chat. Handlers: chatSend, gameList, gameManifest.

lobbyState bundles everything a freshly-signed-in client needs in one message: server info, the caller's own account, every online user, every open room, every available game (with set/starter-deck summaries), and recent chat history — avoiding a flurry of separate round trips on login. After that, incremental changes are pushed via the narrower users/rooms/games/serverInfo broadcast types.

handleChat branches three ways by payload shape: a tradeId defers to trade.go's handleTradeChat; a roomId appends to that room's own 100-line chat buffer and sends only to that room's members; neither means lobby chat, persisted via Store.AddChat (trimmed server-side to the admin-configured ChatHistory length) and broadcast to every signed-in client.

allowanceLoop runs on a 5-minute ticker for the lifetime of the server, crediting the configured periodic token allowance to every currently online authed client whose day/week boundary has passed — complementing the on-login grant in auth.go so a player who stays connected across midnight still gets credited without having to reconnect.

rooms.go — rooms & the per-room goroutine

server/internal/server/rooms.go
Room lifecycle (create/join/spectate/leave/reorder seats/start/close) and the single goroutine-per-room concurrency model that owns each running engine.Room.

This is the file where the server's two concurrency domains meet. Server.mu guards lobby-visible, cross-goroutine-shared Room fields (seats, state, players, spectators, chat) — anything another client's handler goroutine might read via roomInfos() or mutate via join/leave. But the live engine.Room itself, and the live/liveSpecs maps of currently-connected table participants, belong exclusively to that one Room's own goroutine ((*Room).loop()) — because engine.go's doc comment says a Room (and therefore its one Lua VM) "must only be used from a single goroutine." Any other goroutine that needs to touch the engine does so by posting a closure onto r.inbox via r.post(f), which loop() drains one at a time — this is the server's way of giving the single-threaded Lua VM safe, serialized access from a highly concurrent Go program, instead of putting a mutex around Lua calls (which gopher-lua states aren't safe for anyway).

(*Room) loop()

The room goroutine's entire body: a select over four cases — drain r.inbox, a 100 ms ticker calling eng.Tick() (timers like fading drawn arrows), a 5-second idle-check ticker that starts an "empty since" clock once len(r.live) == 0 and asynchronously closes the room once that's exceeded the admin-configured RoomIdleTimeoutMin, and r.done (closes the Lua VM and returns).

(*Room) SendTo / Broadcast

Implements engine.Sink — looks the recipient id up in r.live or r.liveSpecs (room-goroutine-only maps, safe without a lock) and writes a pre-encoded line directly to that client's proto.Conn.

Room creation (handleRoomCreate) enforces a per-room seat cap (maxSeats = 8) and an optional server-wide room-count cap (Settings.MaxRooms). Joining mid-game (handleRoomJoin) is only allowed for someone who already holds a seat — i.e. reconnecting — exactly like the client's own reclaimableIdCheck mechanism for direct peer hosting, just enforced by seat membership instead of a callback. handleRoomStart resolves each shared zone's built-in starting deck from the game library, marshals the seat list (in seat order — the order handleRoomSeats lets the room's owner rearrange beforehand) and posts a closure that actually calls engine.StartRoom on the room goroutine.

collectionBlocked/forwardToRoom add one small but important rule on top of pure message-forwarding: in a collection-mode room, a handful of message types that would conjure cards a player doesn't own (opening the free-for-all Pack Generator widget, creating a card straight from the Card Library, or loading a deck the collection can't back — checked via checkDeckAgainstCollection in decks.go) are rejected server-side with a toast rather than forwarded into the engine at all, regardless of what the client-side UI did or didn't already prevent.

decks.go — decks, collections & packs

server/internal/server/decks.go
Server-kept decks (deckList/deckGet/deckSave/deckDelete) and collection-mode currency spending (collectionGet, packBuy, starterBuy).

handlePackBuy gathers a set's collectible cards (Collectible() excludes unownable and always-free cards — see games.go), runs them through engine.OpenPack (the same Lua pack algorithm the client's widget uses), and only then calls Store.BuyPack to atomically deduct tokens and add the resulting cards — so a pack that happens to come up empty costs nothing ("noCards" failure, no tokens spent). handleStarterBuy similarly sells one of a game's starter decks: it strips the isStarter flag from the deck JSON before saving it as a normal player deck, and auto-suffixes the deck name ("Starter Deck 2", etc.) if the player already has one by that name.

deckShortfall is the human-readable half of collection-mode deck validation: given what a deck needs and what the collection owns, it lists (capped at 3, plus an "and N more") which cards fall short, formatted as "Title (owned/needed)" — surfaced to the player as a toast from rooms.go's forwardToRoom.

trade.go — player-to-player trading

server/internal/server/trade.go
Two-party collection trading: an invite/response handshake, a live offer-editing session, and an atomic swap. Handlers: tradeRequest, tradeRespond, tradeOffer, tradeConfirm, tradeLeave, tradeCollectionGet.

Trading is modeled as two short-lived types, both guarded by Server.mu just like a Room's lobby-visible fields: a pendingTrade (an outstanding invite, auto-expiring after pendingTradeTimeout = 30s via time.AfterFunc) that becomes a Trade once accepted. Each side's tradeOffer is keyed by the id of the user who would receive those cards — i.e. "what I'm asking the other person for" — which is why handleTradeConfirm's final swap reads as "a gives up what b asked for; b gives up what a asked for." tradeEligible blocks starting a trade while already in a room or already mid-trade, checked for both parties before an invite is even sent.

Editing an offer (handleTradeOffer) clamps the requested quantity to what the giving player's collection (t.otherID) actually holds, and silently un-confirms both sides whenever either offer changes — so a late edit can never sneak past a swap the other player already locked in. handleTradeConfirm only executes the swap once both sides have confirmed the current state, via Store.ExecuteTrade — one SQL transaction that re-checks both parties still actually own what they're giving up before moving anything, failing the whole trade atomically (and un-confirming both sides) if a collection changed out from under it (e.g. the player spent those cards in a game started on another trade).

admin.go, admin_files.go, admin_games.go — administration

server/internal/server/admin.go
Account administration: list/update/delete users, kick, server settings, rescan the games folder, clear a collection.

All handlers here are registered in adminHandlers, so Client.handle (server.go) rejects them with notAdmin before they even run for a non-admin. handleAdminUserUpdate is the single richest endpoint: it can rename, re-email, promote/demote admin status, enable/disable, reset a password, and set-or-add tokens in one call — but refuses to demote or disable the last remaining admin (AdminCount() <= 1 check, mirrored in handleAdminUserDelete), so a server can never end up adminless. Disabling or deleting an online user immediately kicks their live connection (reason: "accountDisabled" / "accountDeleted") — matching the exact disconnect-reason strings server_client.lua's DISCONNECT_MESSAGES table translates into user-facing text.

server/internal/server/admin_files.go
Browse and delete a game's files on disk, for the admin Files tab.

gameFileRoot is the load-bearing security check here: it resolves an admin-supplied slash-separated relative path against the game's real folder by cleaning it as an absolute path first (filepath.Join(separator, path) then filepath.Clean) before re-joining it under the game's folder — a ../../etc/passwd-style escape attempt collapses harmlessly inside the fake root rather than reaching outside the game's own directory. handleAdminFileDelete additionally refuses to delete the game's own folder root or a non-empty directory, and triggers a library rescan afterward so the in-memory manifest reflects the change immediately.

server/internal/server/admin_games.go
Remove a game entirely, or install a new one from an uploaded zip. Handlers: adminGameDelete, adminGameInstall.

handleAdminGameInstall re-validates the uploaded zip server-side even though the client already did its own check (admin_game_manager.lua's validateZip) — never trusting the client: it rejects any entry whose cleaned path is .., starts with ../, or is absolute (a zip-slip guard), requires exactly one top-level folder whose name matches the game id declared inside its gamedef.json, enforces a conservative id charset (validGameID), caps total uncompressed size at 512 MiB as a zip-bomb backstop, and refuses to overwrite an id that already exists. Removing a game first force-closes every room currently playing it (s.closeRoom(r, "gameRemoved")) before deleting its folder, so no room is ever left pointing at files that no longer exist.

assets.go — the asset channel

server/internal/server/assets.go
A second, dedicated protocol for bulk file transfer — downloads for every client and admin-only uploads — kept entirely separate from the lobby/game connection so a multi-megabyte file never delays chat or gameplay.

This is the server-side counterpart to the client's asset_sync.lua/asset_worker.lua (downloads) and admin_upload_worker.lua (uploads) — both open a second TCP connection and authenticate it with an assetHello{token} carrying the same session token as the main connection, answered with assetReady. A background goroutine inside serveAssets keeps reading and answering pings on this connection independently, so the idle-timeout clock stays fresh for the whole duration of a long transfer even while the main loop below is busy streaming chunks.

Downloads (assetGet) stream a file in assetChunk (192 KiB, ~256 KB once base64-encoded — matching the client's own 192 KB chunk constant) pieces as assetData messages, using conn.SendWait rather than the normal non-blocking send so a slow client naturally applies backpressure instead of the server's send queue filling up unbounded. Uploads (assetPut, admin-only) are written to a .uploading temp file and atomically os.Renamed into place only once the final chunk (done: true) arrives — so a transfer that's interrupted midway never leaves a half-written file at the real destination path. A gameId: "" upload is special-cased as a flat "staging" write into <games>/.uploads/ rather than into any game's folder — this is exactly the mechanism admin_games.go's handleAdminGameInstall expects a new game's zip to have landed at before it asks the server to install it.

shutdown.go — graceful shutdown

server/internal/server/shutdown.go
Admin-initiated shutdown with a warning countdown, plus auto-shutdown once everyone but the initiating admin has left.

handleAdminShutdown schedules s.Close() DefaultShutdownDelay (5 minutes) in the future via time.AfterFunc, broadcasts a serverShutdown{seconds} message every authed client reacts to (on the client, server_client.lua pops a countdown alert via overlays), and from that moment on refuses any new sign-in or connection attempt (shuttingDown() is checked in both handleConn and handleRegister). shutdownIfEmpty is called after every disconnect and right after scheduling the shutdown itself: if a shutdown is pending and nobody but the admin who started it remains online, it closes immediately rather than making everyone wait out the full delay for an empty server.

internal/store/store.go — SQLite persistence

server/internal/store/store.go
All durable state in one cardflux.db SQLite file, via the pure-Go modernc.org/sqlite driver (no cgo, so the server cross-compiles trivially for Windows/Linux — see build.ps1).

Six tables: users, sessions (only a session token's SHA-256 hash is stored, never the token itself — SessionUser looks up by re-hashing the presented token), decks, collections (card id → quantity per user per game), token_ledger (an append-only audit trail of every balance change and its reason — "starting balance", "pack <game>/<set>", "granted by <admin>", etc.), settings (one JSON blob row) and chat. The connection pool is deliberately capped at SetMaxOpenConns(1) with the comment "SQLite writes serialize anyway; avoids SQLITE_BUSY" — rather than fight SQLite's single-writer nature with retries, the Go side just never contends with itself for a write in the first place. WAL mode and a 5-second busy timeout are set via connection-string pragmas.

Every multi-step mutation is wrapped in an explicit tx, err := s.db.Begin() / defer tx.Rollback() / tx.Commit() — AddTokens (refuses to go negative), BuyPack, BuyStarter (adds cards and saves a deck in one transaction), and ExecuteTrade (re-verifies both parties' holdings inside the same transaction that moves them, described above) — so a crash or a concurrent read never observes a half-applied purchase or trade. NewPeriod is the small pure function deciding whether a daily/weekly token allowance is due, comparing calendar date or ISO week number between the last grant and now.

internal/games/games.go — the game library & manifests

server/internal/games/games.go
Scans <data>/games/<folder>/gamedef.json the same way the client's own game library works, builds a content-hashed file manifest per game, and tracks built-in (embedded) games alongside on-disk ones.

Library.Scan() rereads the whole games directory: for every subfolder containing a gamedef.json it parses just the fields the server actually needs (ids, titles, set/card/zone shape — not the full client-side schema), walks every file with an allowed asset extension (assetExt: images and JSON) while skipping savegames/gamelogs and dot-folders (client-written data that's never part of what a joining player needs to download), and SHA-256-hashes each one. fileHash memoizes by (path, size, mtime) so an unchanged file is never re-hashed on a later rescan. manifestHash folds every file's path+hash into one short digest — this is the value gameInfos()/gameManifest send the client, and what asset_sync.lua's A.ensureGame memo-caches against to skip a completely redundant re-sync. Built-in games (just standard_52 today, from embed.go's EngineFS) get a synthetic single-file manifest and are served straight out of memory via Game.embedded rather than the filesystem.

scanStarterDecks reads every deck file under a game's decks/ folder, keeping only ones marked isStarter (and matching the game's own id) and summing each card's total quantity across every subdeck — exactly the data decks.go's handleStarterBuy needs to credit a collection without re-parsing the deck file itself.

internal/proto/proto.go — the Go side of the wire protocol

server/internal/proto/proto.go
The Go mirror of src/net/protocol.lua: the same one-JSON-object-per-line framing, reimplemented with Go's concurrency primitives instead of LÖVE's per-frame polling.

Where the Lua Connection is polled once per frame from the main thread, Go's Conn runs a dedicated writer() goroutine reading off a buffered channel (out, capacity 4096): SendLine is non-blocking and simply drops the connection entirely (c.Close()) if that queue is ever full, rather than let one slow client's buffer grow without bound — the same "a peer that can't keep up is disconnected" policy Conn's own doc comment states outright. SendWait (used only for asset downloads, see assets.go) blocks instead, because a bulk file transfer legitimately needs backpressure rather than disconnection. The writer goroutine also owns the heartbeat: a HeartbeatInterval ticker sends ping and checks HeartbeatTimeout against the last successful read — identical constants and policy to the client's own P.heartbeatInterval/heartbeatTimeout. Read() answers ping/pong transparently and skips malformed lines, just like the Lua side.

Security notes

Per server/README.md: the wire connection is plain, unencrypted TCP — the LÖVE client's bundled LuaSocket has no TLS support. Passwords are hashed client-side before transmission and bcrypted again server-side for storage, and session tokens mean a password only needs to be typed once per device, but all other traffic (chat, game state, deck contents) travels in the clear. This is explicitly scoped as suitable for "a game server for friends, not a bank." Repeated failed sign-ins are rate-limited (see server.go); there is no outbound email, so a forgotten password can only be reset by an admin via adminUserUpdate's newPasswordHash field.

Development & tooling

The Go module has its own test suite (go test ./..., per server/README.md): internal/engine/engine_test.go exercises the gopher-lua bridge directly, internal/server/server_test.go drives the server end-to-end with fake in-process TCP clients (accounts, rooms, spectating, decks, collections, admin calls — per the README), and version_test.go is the small but important guardrail described above in Why Go embeds a Lua engine: it fails outright if engine/PROTOCOL_VERSION (a one-line file sync-engine.ps1 writes by scraping the client's protocol.lua) doesn't match this build's ProtocolVersion constant, catching exactly the "forgot to re-sync after bumping the client's protocol version" mistake before it ships.

server/tools/sync-engine.ps1 is the one-way copy step described throughout this page: it wipes and rewrites server/engine/ from the sibling client checkout (lib/json.lua, src/core/*.lua, src/game/{session,host_engine}.lua, the standard-52 deck JSON, and the scraped protocol version marker). server/tools/build.ps1 is the release pipeline: run the full Go test suite first (aborting the build on any failure), then atomically increment a BUILD counter file, then cross-compile CGO-free Windows and Linux amd64 binaries into dist/ with that build number baked in via -ldflags -X main.build=N — the same number main.go logs on every startup.
