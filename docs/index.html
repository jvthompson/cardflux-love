What is Cardflux?

Cardflux is a desktop virtual tabletop for card games, built with LÖVE2D and written entirely in Lua. It presents a game table where cards, piles, hands, zones and board widgets (counters, tokens, pack generators, deck-building widgets) can be dragged, flipped, stacked and shared between players — either on one machine for practice/hot-seat play, directly peer-to-peer over LAN/internet with one player hosting, or through a dedicated lobby server that adds accounts, chat, server-kept decks and an optional collection/pack-opening economy. The project is itself a port: much of the code carries comments noting the original .dart file it replaces from an earlier Flutter version of the app, which explains some of its structure (a screen-stack navigator, a profile object, dialog-style overlays) even though none of that Flutter code remains.

What a specific game looks like — its cards, board zones, card sets and rules metadata — is not hard-coded. It's data: a game definition (gamedef.json plus a folder of set images) that ships with the app, is authored/edited in-app, or is downloaded from a lobby server the first time it's needed. One standard 52-card deck ships built in; everything else is just another game definition.

The big picture

The single most important architectural fact about this codebase, mentioned on nearly every page below, is this:

The card-game rules engine is written once, in Lua, and runs in two different places. lib/json.lua, every file in src/core/, and src/game/session.lua + src/game/host_engine.lua have no dependency on LÖVE or the UI. That exact set of files is mirrored byte-for-byte into server/engine/ (kept in sync by server/tools/sync-engine.ps1) and executed inside the companion Go lobby server by gopher-lua, a pure-Go Lua virtual machine. The result: a locally-hosted practice game and a game hosted on the dedicated server run the identical rules code, so the server can referee a game authoritatively without Go ever re-implementing a single game rule. See Core Rules Engine, Game Session & Controller and Cardflux Server (Go) for the full detail.

Three ways a game can be played, and what runs where:

ModeWhere the rules engine runsTransportDocs
Practice / hot-seat Inside the one LÖVE client process None (local only) game.html, ui-screens.html
Direct host & join Inside the hosting player's LÖVE client Raw TCP, optional UPnP port-forward net.html
Dedicated lobby server Inside the Go server, via the embedded Lua engine Raw TCP to cardflux-server server.html, ui-server-screens.html

Everything the player actually sees is drawn by a small, hand-rolled immediate-mode UI toolkit (ui-framework.html) — there's no retained widget tree; every button, dialog and panel is drawn and hit-tested fresh each frame from inside love.draw. Screens are plain Lua tables pushed onto a stack managed by the application shell (architecture.html).

How to read this documentation

Each page below is self-contained and deeply linked to the others, so you can jump straight to whatever you're curious about. If you want a linear path through the whole codebase instead, the sidebar is ordered top-to-bottom as a sensible reading order, and every page ends with a prev/next link that follows the same order. The suggested starting point:

  1. Architecture & App Lifecycle — how the app boots and how screens work.
  2. UI Toolkit (kit) — the primitives every screen is built from.
  3. Core Rules Engine — the data model and rules every game runs on; arguably the most important page in this set.
  4. Game Session & Controller — how a live session is driven, locally or networked.
  5. Then the rest, in whichever order matches what you're investigating.
