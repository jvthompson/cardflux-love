Overview & navigation flow

Every file on this page lives under src/ui/screens/ and is a "screen" in the sense defined by the app shell on architecture.html: a plain Lua table/module instance pushed onto src/app.lua's screen stack (App.push/App.pop/App.replace), exposing some subset of title, showBack, onBack(), draw(x, y, w, h), update(dt), keypressed/keyreleased, textinput, enter()/leave()/resume(), filedropped and quit(). All drawing goes through the immediate-mode widgets documented on ui-framework.html (ui.button, ui.textField, overlays.dialog, etc).

Most of these files are direct ports of a predecessor Flutter app — their header comments name the .dart file they replace, which is a useful cross-reference if you ever find the design history confusing (there is no Flutter code in this repository any more; the comments are historical breadcrumbs only).

The primary navigation graph, ignoring dialogs, looks like this:

Home
 ├─ Host Game ──────────► player_count.host() ─► multiplayer.HostSetup ─► (AssignSeats if 3-4p) ─► HostGameSelect ─► HostGame (the table)
 ├─ Practice Offline ───► player_count.practice() ─► practice_select ─► practice_game (the table)
 ├─ Deck Editor ────────► deck_editor.GameSelect ─► deck_editor.Editor
 ├─ Join a Game (inline)► multiplayer.Join ─► (server detected) server.login lobby, or (raw host) multiplayer.ClientGame (the table)
 ├─ Settings (corner icon) ─► settings_dialog
 ├─ Game Definition Editor (corner icon) ─► gamedef_editor.Entry  (see ui-gamedef-editor.html)
 └─ Support the Author (corner icon) ─► support_dialog

load_saved_game.lua is reached from both the practice and host flows ("Load a Saved Game...") as an alternative to dealing a fresh game. deck_library_dialog.lua, file_picker_dialog.lua, controls_dialog.lua and support_dialog.lua are all opened as overlay dialogs from other screens rather than being destinations in their own right.

home.lua — Home

src/ui/screens/home.lua
The app's landing screen: profile, Join/Host, and secondary actions.

Port of home_screen.dart, extended with an inline Join panel (host/port fields directly on Home, plus one-tap reconnect to the last server) and a responsive layout: a two-column layout once the content area is at least WIDE_BREAKPOINT = 760 logical pixels wide (Home:drawWide), falling back to a single centered column with a Join/Host segmented toggle when narrower (Home:drawNarrow).

Home.new(message) constructs the screen; an optional message is shown as a warning banner (this is how App.popToHome(message) surfaces "You ended the game." / "You left the game." etc back on Home). showBack = false since Home is always the bottom of the stack.

Home.openEditPlayerSettings()
Opens the "Edit Player Settings" dialog (name, color via ui/kit/colorpicker.lua, and an avatar image). Avatar changes are staged in a local st table and only committed to App.profile and src/data/profile.lua when Save is pressed; a chosen avatar is copied in via profile.saveAvatar and invalidated in src/data/image_cache.lua so the new image reloads immediately.
Home.confirmUpdate() / Home.runUpdate()
Port of the update-confirm / update-progress dialogs: confirmUpdate asks to install updater.state.tag (populated by src/platform/updater.lua); runUpdate opens a non-dismissible progress dialog, calls updater.apply(progressCb, doneCb), and on success schedules love.event.quit() ~0.3s later (checked in Home:update) so the external updater helper can swap the install files once CardTable has exited.
Home:drawJoinFields(cx, yy, w, recent) / Home:drawRecentServersPopup(...)
The shared guts of the Join UI used by both the wide Join card and the narrow Join tab: a "LAST PLAYED" banner with one-tap Reconnect when profile.getRecentServers() is non-empty, an IP field with a recent-servers dropdown, a port field, and Connect. Home:connect(host, port) pushes multiplayer.Join with autoConnect = true. Home.joinFieldsHeight(hasRecent) is exposed so callers can reserve exactly the right height without duplicating the layout math.

Home:drawCornerTools draws the three small icon buttons in the bottom-right corner: Settings (settings_dialog), the build icon (Game Definition Editor, see ui-gamedef-editor.html) and a coffee-cup icon (support_dialog). The build number from src/version.lua is drawn bottom-left.

game_picker.lua — Game Picker

src/ui/screens/game_picker.lua
Not a screen itself — a reusable grid-of-game-tiles component embedded by other screens.

Port of game_picker.dart + game_grid.dart. GamePicker.new(onGameChosen, opts) loads the game library folder (src/data/paths.lua's gamesDir()) via src/data/game_loader.lua's loadGamesFromDirectory, always appending the built-in Standard 52-Card Deck game (loader.loadStandardDeck()) unless opts.excludeStandardDeck is set (deck editors hide it since it can't be customized). Loading is deferred to the next update() call (pendingLoad = 2 frames) purely so a progress indicator gets drawn before the (blocking) directory scan runs.

P.drawGrid(scrollId, games, x, y, w, viewH, pad, onTap) is the reusable tile-grid renderer (up to MAX_COLUMNS = 7 columns of 268px tiles) and is also called directly by other screens that want a grid of games without the rest of the GamePicker chrome (e.g. the Game Definition Editor's Entry screen on ui-gamedef-editor.html, and the server's Card Shop screen on ui-server-screens.html). P.gridHeight(w, count) lets a caller size a non-scrolling viewport to exactly fit.

P.maybeMoveLibraryFolder(oldRoot, newRoot, whatLabel, after) (port of move_library_prompt.dart) is the confirmation shown whenever the user picks a new games/decks folder that isn't empty: offers to move the old folder's contents into the new one via src/data/gamedef_ops.lua's moveDirectoryContents. It's reused by chooseDirectory here, by the gamedef editor's folder picker, and by deck_library_dialog.lua's folder picker.

player_count.lua — Player Count

src/ui/screens/player_count.lua
A tiny generic "pick a number" screen, parameterized for Host or Practice.

Ports player_count_screen.dart (host: 2-4 players) and practice_player_count_screen.dart (practice: 1-4 decks) as two factory functions, S.host() and S.practice(), that build the same generic screen (S.new(title, question, counts, labelFor, onChoose)) with different button sets. S.host() pushes multiplayer.HostSetup.new(n); S.practice() pushes practice_select.new(n).

practice_select.lua — Practice Game Select

src/ui/screens/practice_select.lua
Choose a game to practice offline with the chosen number of local seats.

Port of practice_game_select_screen.dart. Wraps a GamePicker and, on choosing a game, builds a PlayerInfo list (see src/core/models.lua) — seat 1 is the local player using their real name/color from App.profile; the remaining seats are "Player 2".."Player N" colored from src/core/color.lua's boardWidgetColorPalette, skipping colors already in use. It then pushes practice_game.new({game, players, deckConfigsByPlayerId = {}}) — an empty (not nil) deck map, since practice mode deals built-deck zones empty and expects each seat to load a deck at the table, same as the Flutter original. A "Load a Saved Game..." button instead routes through load_saved_game.lua.

practice_game.lua — Practice Game

src/ui/screens/practice_game.lua
The screen that actually hosts an offline practice session — one player acting as every seat.

Port of practice_game_screen.dart. Creates a Session — either Session.localPractice(...) for a fresh deal, or Session.new({initialState = loadedState, isLocalPractice = true, ...}) when resuming a save (resuming re-derives the session clock's start time from the save's last log entry's elapsedMs, so elapsed-time displays keep counting from where the save left off instead of resetting to zero). It then builds a TableScreen with controller.Host.new(session) (practice mode is always "hosted" locally, with no network peer — see src/game/controller.lua) and isMirrored = false (practice always sits the local player at the bottom, since they can click any avatar to act as any seat).

S:saveGame() opens src/ui/kit/save_name_dialog.lua pre-populated with existing saves from src/data/save_files.lua, and writes a models.SavedGame (clearing state.searches first, since in-flight search dialogs aren't meaningful to persist). Discord Rich Presence is kept in sync via publishPresence/ src/platform/discord.lua's setPlaying/setIdle, hooked to the session's listener mechanism (see game.html) so presence updates whenever the roster changes.

multiplayer.lua — Host / Join / Play Online

src/ui/screens/multiplayer.lua
The single largest screens file: six screen types covering hosting, joining, and playing a networked game.

Ports host_setup_screen.dart, assign_seats_screen.dart, game_select_screen.dart, host_game_screen.dart, join_screen.dart and client_game_screen.dart into one module (M) exporting HostSetup, AssignSeats, HostGameSelect, HostGame, Join and ClientGame. It pulls together nearly every other subsystem: src/net/protocol.lua, host_server.lua, game_client.lua, netinfo.lua; src/game/session.lua, host_engine.lua, controller.lua, sound.lua; src/data/profile.lua, save_files.lua, deck_library.lua, game_loader.lua; and src/platform/discord.lua for Rich Presence and game invites.

A module-local helper, avatarKeys(bytesById), interns raw avatar PNG bytes into image_cache keys (hashed with love.data.hash("md5", ...)) so repeated calls with the same bytes don't re-register the image. It's exported as M.avatarKeys and reused by HostGame:update and ClientGame:handleMessage to keep the table's avatar images current as players join, leave or change their picture mid-game.

HostSetup (lobby)

HostSetup.new(maxPlayers) immediately starts a HostServer (binding a TCP port) and begins resolving the public IPv4 address via src/net/netinfo.lua. It shows LAN addresses, the public address, and UPnP port-forwarding status for "Manual IP" sharing, or — via a segmented toggle — an "Invite via Discord" mode that lists Discord friends and sends each one a Rich Presence game invite carrying publicIP:port as the join secret (HostSetup:sendInvite, src/platform/discord.lua). Once the roster fills to maxPlayers, HostSetup:update auto-advances to AssignSeats (3-4 players) or straight to HostGameSelect (2 players, where seating order is unambiguous).

AssignSeats

Shown only for 3-4 player games, where the physical seating around the table matters (see src/core/seat_utils.lua). Draws a small schematic of the table (top row / "(shared table)" / bottom row) and a dropdown per seat to swap players into position, then calls server:setSeatOrder(...) and advances to HostGameSelect.

HostGameSelect

Wraps a GamePicker for the host to choose which game to play (or "Load a Saved Game..."). resolveSharedDeckConfigs(game) pre-resolves any shared zone that names a deckName (rather than being a player-built deck) by looking it up in src/data/deck_library.lua, so HostGame doesn't need to touch the filesystem again.

HostGame

The actual hosted table. Broadcasts gameData to every connected client immediately, builds the Session (dealt fresh via Session.dealFromZones, or resumed from a save), then creates a HostEngine that owns authoritative game-rule enforcement and starts it. controller.Host.new(session, engine) is handed to the TableScreen so local input goes through the same validation path remote clients' messages do. HostGame:endGame disposes the engine, stops the server (reason "hostLeft", which ClientGame below turns into a user-facing message) and pops back to Home with a confirmation banner.

Join

The client half of connecting: an IP/port form (with the same recent-servers dropdown pattern as Home) that, on Connect, creates a GameClient and watches its onStatus callback. A status of "server" means the address turned out to be a full CardTable lobby server (not a direct peer-to-peer host) — the screen hands the raw connection to src/net/server_client.lua's adopt and replaces itself with src/ui/screens/server/login.lua. A status of "connected" with an assigned player id means a direct game host accepted the connection — the screen saves a reconnect token (profile.saveReconnect, keyed by host:port, consumed on a later reconnect attempt) and replaces itself with ClientGame.

ClientGame

The client-side table screen, driven entirely by messages from the host (client.onMessage routed into ClientGame:handleMessage). It is reused, via its opts table, both for a direct peer-to-peer game and for a game running on a CardTable server (where client is actually server_client:gameChannel() — see ui-server-screens.html's room.lua): opts.localGame supplies locally-cached game art so a server game doesn't need every image round-tripped over the network, opts.onExit redirects "leave" back to the server lobby instead of all the way Home, and opts.spectator/opts.collectionMode/ opts.deckStore flow straight through to TableScreen.

Message handling builds up the session lazily: gameData gives the GameDefinition (run through resolveLocalImages to merge in any locally-cached art), lobbyRosterUpdate tracks who's connected and their avatars before the game itself starts, and the first fullState message constructs the Session and the TableScreen (with controller.Client.new(sendFn) — every local action is sent to the host rather than applied directly). Subsequent fullState messages go through session:applyRemoteState instead. cardDragPreview(End) and arrowDragPreview(End) messages update the live cursor-drag/arrow previews other players see while someone is mid-drag (see ui-table.html).

load_saved_game.lua — Load a Saved Game

src/ui/screens/load_saved_game.lua
Browse a game's saves and resume one, remapping saved players onto the current seats.

Ports load_saved_game_screen.dart and seat_match_screen.dart. Step one is a GamePicker to pick which game's save folder to browse (src/data/save_files.lua's listSaveGames); step two lists that game's saves, graying out ones whose playerCount doesn't match the current session's player count.

Picking a compatible save calls remap.matchPlayersByName (src/core/save_remap.lua) to pair saved players to current players by name. Any saved player that can't be matched automatically triggers the nested SeatMatch screen — a dropdown per unmatched saved player to manually choose which current player they now are — before finally calling remap.buildLoadedTableState to produce a TableState with ids rewritten onto the current roster, dropping (with a confirmation if any exist) cards whose definition no longer exists in the game (it may have been edited in the Game Definition Editor since the save was made).

deck_editor.lua — Deck Editor

src/ui/screens/deck_editor.lua
Build/edit a DeckConfig: a card pool on the left, the deck list on the right.

Ports deck_editor_game_select_screen.dart and deck_editor_screen.dart. Exports { GameSelect, Editor, buildSlots }. GameSelect is a thin GamePicker wrapper (excluding the Standard 52-Card Deck, which can't be customized); picking a game opens Editor.new(game, opts).

buildSlots(game)
A deck isn't always one list: a game can declare multiple deck-building zones with distinct deckTypes (e.g. a main deck and a separate sideboard). This builds one "slot" per distinct deckType found among GameDefinition.deckBuildingZones(game) (see src/core/models.lua), labeled by the first zone that uses it, required unless every zone using it has deckOptional set — or, if the game declares no deck-building zones at all, a single implicit main_deck slot.

Left-clicking a pool card calls E:addCopy(id); right-clicking calls E:removeCopy(id). Quantities are tracked per slot as an insertion-ordered map ({order = {...ids}, qty = {id = n}}) so the saved file and on-screen deck list preserve the order cards were added, matching the original Dart Map semantics. E:saveDeck() and E:openDeck() delegate to deck_library_dialog.lua's promptSaveDeck/open.

Collection mode. When opened with opts.ownedQty (a server's collection-mode deck editor — see ui-server-screens.html), the pool is filtered down to owned, unownable or isFreeCard cards (E:visibleCards), copies are capped at the owned quantity (E:ownedLimit/E:addCopy), and E:clampToCollection trims any over-the-limit copies left over after loading a deck built before a collection shrank (e.g. cards sold or lost). opts.store (a src/data/deck_store.lua store) redirects Open/Save at a server instead of the local deck library folder.

deck_library_dialog.lua — Load/Save Deck dialog

src/ui/screens/deck_library_dialog.lua
The 760×560 "Load Deck" overlay opened at the table, plus the Save Deck flow shared by the Deck Editor and the table.

Port of widgets/deck_library_screen.dart, rendered as an overlays.dialog rather than a full screen. D.open(game, zones, onDeckChosen, opts) lists every deck for the game — either from the local folder (src/data/deck_library.lua's loadAllDecksForGame) or, when opts.store.kind == "server", from a server's deck list (deck_store.lua) — as a grid of card-back tiles sized like the Deck Editor's pool. zones (the ZoneDefinitions being filled) drives validation: a deck missing any non-optional zone's deckType is rejected with an inline error rather than loaded (missingRequired).

Right-clicking a non-built-in deck opens a context menu to delete it (deleteDeck, routed through the store for server decks or src/data/fs.lua's remove locally). "Browse for file..." (local only) opens file_picker_dialog.lua to load an arbitrary deck JSON from disk via decks.readDeckFile, rejecting legacy-format files with a pointed error message (models.LegacyDeckFormatError).

D.promptSaveDeck(game, deck, onSaved, opts) opens src/ui/kit/save_name_dialog.lua pre-filled with existing deck names to reuse; for a server store it delegates to D.promptSaveServerDeck, which additionally offers an "Also save a copy to my local deck library" checkbox (store.alsoLocal).

file_picker_dialog.lua — In-app file picker

src/ui/screens/file_picker_dialog.lua
A from-scratch, overlay-based file/folder browser that replaces the OS-native picker.

Added to work around a DWM bug: the native Windows file dialog (see src/platform/ file_dialog.lua) has an unfixable z-order quirk when CardTable's borderless, fullscreen-shaped window is maximized, and there was no native implementation at all on Mac. This module reimplements a minimal browser — up-one-level, refresh, an editable path field, and a scrollable listing (directories always shown, files filtered by the caller's extension list via extensionSet) — entirely as an overlays.dialog, exposing the same opts shape (title, filters, initialDir) the old native-dialog wrapper used, so callers didn't need to change. M.openFile(opts, onResult) and M.pickFolder(opts, onResult) both resolve asynchronously: onResult(path) fires exactly once, with nil on cancel.

This is a good example of the "in-app overlay with an async callback" pattern used throughout the UI for anything that would otherwise need a blocking native dialog — the same shape shows up in deck_library_dialog.lua and save_name_dialog.lua.

controls_dialog.lua — Controls (Markdown renderer)

src/ui/screens/controls_dialog.lua
A tiny hand-rolled Markdown parser/renderer, built to display CONTROLS.md in-app.

Rather than maintain the controls reference in two places, this module parses the actual CONTROLS.md file shipped inside the .love archive (packed in by tools/build.ps1) at runtime, so the in-app dialog and the file in the repository can never drift apart. M.parse(text) understands the small subset of Markdown the file actually uses — #/ ##/### headings, pipe tables (with the |---| separator row discarded), - bullets, a whole-line **bold** treated as a sub-heading, and plain paragraphs — and reduces it to a flat list of typed blocks. M.drawBlocks(x, y, w, list) renders that block list with the app's own text/table widgets. M.loadBlocks(source) caches the parsed result by file path so it is only parsed once per path.

This parser is intentionally generic over its source file — support_dialog.lua reuses M.loadBlocks/M.drawBlocks directly to render SUPPORT-ME.md instead.

settings_dialog.lua — Settings

src/ui/screens/settings_dialog.lua
The app preferences dialog, opened from Home and the in-game menu.

A single dialog organized into labeled sections (the file's own header comment says new settings should be added as new sections): Display (UI scale dropdown, sourced from App.uiScaleOptions and written back via App.setUiScaleSetting — see architecture.html's discussion of scale), Appearance (dark mode, persisted through src/data/profile.lua's setDarkMode), Hand (sliders driven by src/data/hand_settings.lua's declarative defs list — applied live while dragging, saved only once the slider is released) and Table (the selection highlight color, via src/data/table_settings.lua and colorpicker.lua).

opts.inGame changes the Appearance section's subtitle to note that the game table always renders in the light theme regardless of the dark-mode setting (see forceLightTheme on src/app.lua).

support_dialog.lua — Support the Author

src/ui/screens/support_dialog.lua
A small dialog pointing to the author's Ko-fi page, rendering SUPPORT-ME.md.

The simplest screen file in the app: it reuses controls_dialog.lua's Markdown renderer wholesale to display SUPPORT-ME.md, with a "Visit Ko-fi.com" action button that opens M.kofiUrl via love.system.openURL.
